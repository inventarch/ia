# Product distribution packing

The public packer creates candidate archives from the reviewed source selection. It does not publish them.

`.ia/public-package-inputs.json` seals the reviewed tracked selection for release preparation. `pnpm release:version` refreshes it on the release branch (`pnpm npm:inputs` does so directly), recording only the public repository commit, tree, working-copy state, file digests and package versions. Release preparation and publication refuse a stale seal. Ordinary qualification packs the selection the checkout would seal, computed in memory with the same package identity and membership refusals against `packageNames` in `tools/distribution/public-content-policy.json`, so a pull request does not rewrite the descriptor. A dirty, stale or changed archive is not a publication qualification. The v2 seal drops obsolete extraction metadata. The content policy is the reviewed membership owner, including each package’s private/public bit; adding a package requires editing that policy. The v2 compatibility companion binds the same public provenance, membership digest, recipe and archives.

Native archive versions are independent from the npm cohort and syntax headers. `pnpm native:version` previews the content-driven selection; `pnpm native:version --write` updates system declarations, their public language copies, the native policy and `releases/native/current.json`. It never publishes or changes npm versions. `pnpm native:release:check` rebuilds every selected native archive, compares it with published evidence and refuses stale selection, changed bytes under a published identity/version, or a stale candidate ledger. The platform gate and npm preparation require this check.

The one-time transition from the twelve native archives shipped in npm 2.0.0 selects 2.1.0 through an explicit alignment in `releases/native/notes.json`. This is independent of the next npm version computed from npm notes. Subsequent native notes name each changed archive with patch, minor or major impact and a reviewable summary, against the latest reachable published `v<version>` tag. Repacking at the published native versions distinguishes content changes from version-only edits. Changed exact dependency versions also change their consumers' bytes; each affected consumer needs its own note, including the language archive when its embedded system declarations change. Unchanged archives retain their published native version even if a note requests a bump. Removing or adding a native identity requires a separately reviewed membership migration.

For npm 2.0.0, `releases/native/baselines/npm-2.0.0.json` pins the public tarball SHA512 integrities and native SHA256 digests, verified from the registry; the gate binds that file and the published tag commit to fixed digests. Later baselines come only from `releases/native/current.json` inside the newest reachable immutable release tag, never from the candidate's mutable ledger. Full release tags must be available locally. Notes and the candidate ledger remain reviewable with the release; after publication, replace the notes' baseline and entries for the next content change. A previous release's notes cannot authorize new changes.

Regenerate public assets after native selection and rerun the native version writer if generated native inputs change. Then select the npm cohort with its separate release tool, reseal, commit and qualify exact archives and installed consumers. An untagged local native or npm selection is preparation, not release approval. Rolling back an unpublished selection means restoring its source declarations, policies and ledger together from the prior commit and regenerating assets; published native bytes and tags are immutable.

`pnpm npm:prepare` builds, validates generated public assets and public behavior, packs the selected archives and retains their digests and compatibility evidence. `pnpm npm:plan` verifies the exact receipt before producing publication commands. Repository release permissions and an explicit publication decision remain separate.

## Coordinated npm releases

`releases/current.json` selects one version for every public npm package, the published source baseline, the publication tag and complete allowed dependency cycles. Native-system and protocol versions remain independent. A new npm release must advance its published baseline and consume a reviewed changeset under `releases/changesets/<version>.json`. A version is published when its immutable `v<version>` tag exists; the publishing workflow creates the tag only after registry verification.

Unreleased package changes are described by pending notes under `releases/pending/`. `pnpm release:check` requires a note for every public package changed outside the prepared release's coverage, and refuses a published changeset that differs from its tagged bytes. `pnpm release:version` applies the largest pending bump to the published baseline. It moves every cohort manifest, the editor extension, its dependency notices and each system's `npmVersion` together, then consumes the notes into the changeset. While a prepared release is untagged, the release workflow leaves it unchanged; a maintainer may amend or refresh it explicitly.

The changeset names every public package with either described changes or a justified cohort-only entry. It groups user-facing changes and binds every changed tracked file since the baseline to a change entry and its exact SHA256 (or deletion). Changed files outside every package may belong to an internal entry that names no package and is omitted from the changelog. Only the self-referential changeset, generated changelog and public input descriptor are excluded from that file list; their exact bytes are sealed by the release receipt or existing input boundary. Unlisted files, missing packages, unknown packages, unconsumed entries, pending notes, stale coverage and changed historical entries refuse `pnpm release:check --strict`, which release preparation runs. Commit coverage is derived from Git history and retained with the exact source revision. Machines establish coverage and freshness; a reviewer checks semantic accuracy in the release pull request, and the `npm` environment approval accepts the changeset digest at publication.

Publication receipts are version2 and retain the actual packed dependency graph. Strongly connected components are ordered before their consumers; a cycle must exactly match a reviewed complete group. Uniform versions cannot eliminate cycles or make sequential npm publication atomic. Every internal packed dependency must name a selected package at the exact cohort version.

A registry preflight checks the whole cohort before writes, refuses newer registry versions and conflicting immutable bytes, and permits retry only for identical archives with the expected tag. A separate read-only verification job checks all final registry versions, downloaded bytes, latest tags and provenance, then installs the exact registry cohort with scripts disabled and runs npm signature/attestation verification. An interrupted publish remains partial until the complete verification succeeds; neither a preparation run nor package existence proves trusted-publisher authorization.
