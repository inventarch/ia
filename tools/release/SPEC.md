## Commands

- `pnpm npm:inputs`: `node tools/release/public-pack.mjs refresh-inputs`.
- `pnpm native:version`: `node --conditions=development --import tsx tools/release/native-version.ts`.
- `pnpm native:release:check`: `node --conditions=development --import tsx tools/release/native-version.ts --check`.

Commands report success as exit 0 and evaluated failure as exit 1. Corrected strict parsers use exit 2 for usage errors. Existing command-specific defaults, flags and refusal behavior are described below; a check never implies a write.

## Inputs

Explicit package/content policies, tracked source selection, native selectors, release input seal, source revision and platform/runtime coordinates.

## Outputs

Packing writes owned staging/archives/receipts. Input resealing and native version --write are explicit release preparation effects.

## Prerequisites

Pinned package manager and build dependencies; sealed release consumers require current source/input evidence.

## Validation

Task ownership: `native:release-check`, `tools:test-public-release`, `tools:test-native-release`. `tools/testing/tasks.json` declares platform, timeout, prerequisite, output and input-profile contracts; `nx.json` defines their actual file/runtime inputs. Live discovery and mutation tests validate coverage and caching.

## Invariants

Consumers verify archive digests and receipt identity. Public content scans remain mandatory. No changed recipe is silently interpreted as an older receipt.

`ia.packing-recipe.v1` preserves the existing v2 companion's explicit 26-file selection, including its historical documentation/test entries. Producer, verifier and archive fixtures call the same selector. Selection preserves source-row order, refuses missing or duplicate inputs and invalid digests, and never grows because a file was added to a directory. The full-source input descriptor still binds every tracked implementation, including the recipe module itself and helpers outside this selection; extraction does not weaken or replace that binding. A frozen pre-extraction row fixture proves byte and digest parity. The recipe test walks tooling import syntax transitively and requires exact agreement with the separate reviewed implementation list; new side-effect imports, re-exports, aliases or dynamic imports must be accounted for explicitly. The guard resolves file-URL imports, explicitly lists relative product entrypoints outside tools, and refuses the module loader however it is reached: `node:module` through static, aliased, re-exported, dynamic, `require` or `import = require` edges, and any `getBuiltinModule` reference. Full package qualification exercises production companion generation and verification. Runtime package sources remain bound by the full-source descriptor.

The companion format stays `ia.system-package-compatibility.v2`. A different recipe membership or final directory rename requires the release-boundary migration and new qualification; this extraction neither reseals existing inputs nor treats old evidence as current.

## Limits

This remains the packing owner during the approved intermediate migration. The final packing/release rename and fresh release seals require the separate maintainer checkpoint.

## Detailed behavior

The public packer creates candidate archives from the reviewed source selection. It does not publish them.

`packOptionalDistribution` reads filesystem-selected native sources and assets through checked descriptors. Each read must match the observed regular, single-link file identity and metadata before consuming bytes, stays within the existing distribution file ceiling and the observed size, and rechecks descriptor, path and containment before admitting bytes. Substitution or change refuses the candidate. Already-selected asset buffers retain their caller-owned selection. These checks do not lock the directory or create an atomic snapshot of its entire mutable tree; POSIX no-follow and nonblocking flags are used where the platform exposes them.

`.ia/public-package-inputs.json` seals the reviewed tracked selection for release preparation. `pnpm release:version` refreshes it on the release branch (`pnpm npm:inputs` does so directly), recording only the public repository commit, tree, working-copy state, file digests and package versions. Release preparation and publication refuse a stale seal. Ordinary qualification packs the selection the checkout would seal, computed in memory with the same package identity and membership refusals against `packageNames` in `tools/distribution/public-content-policy.json`, so a pull request does not rewrite the descriptor. A dirty, stale or changed archive is not a publication qualification. The v2 seal drops obsolete extraction metadata. The content policy is the reviewed membership owner, including each package’s private/public bit; adding a package requires editing that policy. The v2 compatibility companion binds the same public provenance, membership digest, recipe and archives.

`public-content.test.ts` also keeps every tracked file, except the consumed changesets and the changelog generated from them, free of pointers to private planning material: the names of documents, decisions and repositories kept outside this repository, pinned by word count, length and SHA-256 as `public/content-scan.mjs` pins its denied tokens so that the test does not list them, and phrasing that points at a private knowledge base's tasks or decisions. The guard reports every occurrence by file and line and verifies the exact counts of the documented release-dependent exceptions. Cite the public SPEC clause that states a rule instead.

Native archive versions are content-driven within an npm major. A release whose stable npm target in `releases/current.json` starts a new major aligns every public native archive to that target, changed or not; that target must be the major's `x.0.0`. The npm versioner only ever selects that; a later target, reachable only by editing `releases/current.json` by hand, refuses in the native writer and in the shared selector rather than aligning natives to it. Within a major, an archive whose normalized bytes differ from its last published version, directly or through a changed exact dependency, moves from that version by its own native note; every other archive keeps its published version and bytes. No native version may pass the npm target. `pnpm native:version` previews that selection; `pnpm native:version --write` updates the exact system declaration version fields, their public contract copies, both native policies, the composition fixture's exact bundled-language dependency range and `releases/native/current.json`. It does not publish or change npm package manifests; each system policy row's `npmVersion` follows the npm target while its native version follows this rule. A shared Node-builtins-only selector serves this writer and the npm versioner; malformed or incomplete native surfaces refuse before writes. Syntax headers, schemas, formats, engine requirements and protocol numbers remain unchanged. `pnpm native:release:check` rebuilds every selected native archive, compares it with published evidence and refuses stale selection, changed bytes under a published identity/version, or a stale candidate ledger. The platform gate and npm preparation require this check.

The twelve native archives shipped in npm 2.0.0 retain their immutable native 1.2.0 baseline; the npm 3.0.0 major aligned all twelve to 3.0.0. Native notes name each changed archive with patch, minor or major impact and a reviewable summary against the latest reachable published `v<version>` tag. Within a major, a note selects its archive's next version from the published one, so a major-impact note needs a major npm release; at a new major a note only sets the minimum the npm target must satisfy. The obsolete one-time alignment field refuses. Repacking at the published native versions distinguishes content changes from version-only edits. Changed exact dependency versions also change their consumers' bytes; each affected consumer needs its own note, including the language archive when its embedded system declarations change. Unchanged archives keep their published version within a major and move, without a note, only at a new major. Removing or adding a native identity requires a separately reviewed membership migration.

For npm 2.0.0, `releases/native/baselines/npm-2.0.0.json` pins the public tarball SHA512 integrities and native SHA256 digests, verified from the registry; the gate binds that file and the published tag commit to fixed digests. Later baselines come only from `releases/native/current.json` inside the newest reachable immutable release tag, never from the candidate's mutable ledger. Each native version in such a tagged ledger must lie within the tag's major and at or below the tag itself; any other refuses. Full release tags must be available locally. The latest native tag and commit must match npm's published baseline for an unpublished target. Notes and the candidate ledger remain reviewable with the release; after publication, replace the notes' baseline and entries for the next release. When no native archive changed since, the npm versioner does that itself (below). A previous release's notes cannot authorize new changes. Every unpublished target requires the complete freshly derived ledger, including baseline and notes digest, even when normalized content is unchanged. Only an unchanged target exactly matching the newest reachable published release can use that release's historical ledger; published identities and bytes remain immutable.

The npm versioner moves each system policy row's `npmVersion` with every release, and moves the native selectors only for a new major, on new releases and explicit same-version refreshes. It does not regenerate or qualify native archives, and it never selects a content-driven native version; when the native selection moves or native notes target the release, its pull request description keeps the regeneration instructions. Otherwise, a ledger still equal to the one the npm baseline's tag carries means no archive changed since that tag, because the native check refuses a changed archive without notes against it. The versioner then carries that ledger forward: its archives stand, its baseline becomes the tag and its notes digest follows the notes, which, when they target an earlier tag, reset to an empty set for this one. That is the ledger `pnpm native:version --write` would write, and `pnpm native:release:check` on the release head still verifies it. A ledger that moved since the tag stays with the native writer. Regenerate vocabulary, public and authoring assets, run the native version writer, and repeat to a fixed point when generated native inputs change. Regenerate projections, commit, and run `pnpm release:version --write --refresh`, which re-collects release coverage, including generated alignment for native version fields the selection moved, and reseals the final tracked inputs; collection alone cannot add that generated coverage. Commit and qualify that exact prepared head and installed consumers, making each of those commits a release preparation commit under the rule in [NPM-PUBLISHING.md](../distribution/NPM-PUBLISHING.md). When regeneration is required, both release PR description forms retain it. An untagged local native or npm selection is preparation, not release approval. Rolling back an unpublished selection means restoring its source declarations, policies and ledger together from the prior commit and regenerating assets; published native bytes and tags are immutable.

`pnpm npm:prepare` builds, validates generated public assets and public behavior, packs the selected archives and retains their digests and compatibility evidence. `pnpm npm:plan` verifies the exact receipt before producing publication commands. Repository release permissions and an explicit publication decision remain separate.

## Coordinated npm releases

`releases/current.json` selects one version for every public npm package, the published source baseline, the publication tag and complete allowed dependency cycles. The public native-system and language-archive artifact versions align with that target only at a new major, and are otherwise content-driven (above); syntax and protocol versions remain independent. A new npm release must advance its published baseline and consume a reviewed changeset under `releases/changesets/<version>.json`. A version is published when its immutable `v<version>` tag exists; the publishing workflow creates the tag only after registry verification.

Unreleased package changes are described by pending notes under `releases/pending/`. `pnpm release:check` requires a note for every public package changed outside the prepared release's coverage, and refuses a published changeset that differs from its tagged bytes. While a release is prepared but untagged, it also refuses native version metadata missing or different from the changeset's coverage, including a recorded native version-only path restored to its baseline bytes and therefore absent from the current diff. Package manifest formatting and private package versions are outside this native coverage guard; public npm versions remain checked against the cohort. Ordinary semantic edits still use pending notes rather than publication's exact-byte coverage check. On the release branch this catches before merge what publication's strict check, which reads the release merge commit, would refuse after it, and `pnpm release:version --write --refresh` repairs it in a release preparation commit under the rule in [NPM-PUBLISHING.md](../distribution/NPM-PUBLISHING.md). Main and every branch from it stay prepared from the release merge until publication tags it, so in that window an ordinary pull request whose `pnpm native:version --write` moved a native version is refused too. It waits for the tag and updates from main, as it would have to anyway: once the tag exists, `pnpm native:release:check` refuses the same branch until its native notes target the new tag. A contributor never refreshes the consumed changeset. `pnpm release:version` applies the largest pending bump to the published baseline. It moves every cohort manifest, the editor extension, its dependency notices and each system policy row's `npmVersion` together, and the native selectors only for a new major, then consumes the notes into the changeset. An explicitly requested refresh repairs stale native selectors even when npm coverage is already current. A later failure restores every touched selector, manifest, note, carried native ledger, changeset, changelog and input descriptor; archive-ledger generation beyond that carry remains a separate operation. While a prepared release is untagged, the release workflow leaves it unchanged; a maintainer may amend or refresh it explicitly.

The changeset names every public package with either described changes or a justified cohort-only entry. It groups user-facing changes and binds every changed tracked file since the baseline to a change entry and its exact SHA256 (or deletion). Generated `cohort-alignment` coverage applies only to an exact named file freshly proven to change approved version metadata alone. The proof covers package manifests, selected system declaration fields, public contract copies and native policies; semantic, identity, membership, dependency, header, new/deleted and lookalike changes cannot reuse it. The sole dependency exception is the exact `apps/cli/tests/fixtures/composition-workspace/.ia/release.json` reference to the selected `inventarch/language` artifact: only its unique canonical caret range may change; every other descriptor value and system identity must remain equal. Generic repositories may omit this fixture; both writers synchronize it when present, and native check refuses a stale range. Collection and strict validation share that applicability rule, regardless of package impact kind, and collection can fall back to a legitimate authored scope. Named packages whose note covers only another file still receive correctly owned exact metadata coverage. Semantic package edits must have authored coverage before generated entries are added. Changed files outside every package may belong to an internal entry that names no package and is omitted from the changelog. Only the self-referential changeset, generated changelog and public input descriptor are excluded from that file list; their exact bytes are sealed by the release receipt or existing input boundary. Unlisted files, missing packages, unknown packages, unconsumed entries, pending notes, stale coverage and changed historical entries refuse `pnpm release:check --strict`, which release preparation runs. Commit coverage is derived from Git history and retained with the exact source revision. Machines establish coverage and freshness; a reviewer checks semantic accuracy in the release pull request, and the `npm` environment approval accepts the changeset digest at publication.

Publication receipts are version2 and retain the actual packed dependency graph. Strongly connected components are ordered before their consumers; a cycle must exactly match a reviewed complete group. Uniform versions cannot eliminate cycles or make sequential npm publication atomic. Every internal packed dependency must name a selected package at the exact cohort version.

A registry preflight checks the whole cohort before writes, refuses newer registry versions and conflicting immutable bytes, and permits retry only for identical archives with the expected tag. Each packument read names an npm package name (an optional lowercase scope, then lowercase letters, digits, `.`, `_` and `-`, led by a letter or digit); any other name refuses before a request is made. A separate read-only verification job checks all final registry versions, downloaded bytes, latest tags and provenance, then installs the exact registry cohort with scripts disabled and runs npm signature/attestation verification. An interrupted publish remains partial until the complete verification succeeds; neither a preparation run nor package existence proves trusted-publisher authorization.
