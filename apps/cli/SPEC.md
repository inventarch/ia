Suggested commands omit roots containing shell syntax and use `.` with an explicit workspace-directory instruction. Inert Windows roots use forward slashes so Git Bash, PowerShell and cmd address the same directory. Directory instructions accompany only an actual replacement with `.`; separator normalization alone keeps a relative command in its original directory, even when a resolved root alias contains shell syntax. Unknown-command advice parses a supported nearest command before preserving its arguments, otherwise it names that command's help without reading the filesystem. Generic interruption advice rebuilds parsed option values and the init positional target, covering equals options and options placed before a target. A value matching a declared option token retains equals spelling, including short aliases and help flags; normalization retains `./` for an init target beginning with a dash. `tests/refusal-next.test.ts` reparses and reruns printed advice to verify the value and target survive. For a fresh absent init target whose path is omitted, preview first instructs the operator to create and enter that target without pasting the active path into a shell, then run the printed apply command; preview itself creates nothing.

Shell-safe root remedies: refusal and profile next actions, interruption remedies, doctor command suggestions and session briefing, already-initialized init guidance and capture-preview commands never repeat a known root containing shell-active characters. They preserve the command and use `--root .` (or the positional `.` for init), with an explicit instruction to run it from the workspace root. The exact supplied, resolved and observed real root are matched as data before display; no shell parser or command execution is used. Ordinary roots, including spaces, retain their existing quoting. Capture previews construct portable commands from the exact supplied root, including relative Windows roots; their JSON snapshot paths retain native spelling. Root diagnostics and briefing argument vectors still identify the actual path; the briefing's plain host command uses the safe spelling and its accompanying context and notice explain the required directory. This supersedes the earlier exemption of the caller's root from the inert-next rule. The runtime's conservative mandate admission policy is unchanged.

The `ia` binary exposes consumer commands and the structured agent query protocol. The [language reference](https://github.com/inventarch/ia/blob/main/docs/reference/language/README.md) defines vocabulary and evaluation limits, and the packaged [language summary](LANGUAGE.md) lists the words this release ships. This package bundles the language archive, vocabulary catalogue and host payload needed by its commands.

## Workspace commands

An actor must be established before a mandate naming a participant supplies its grants. A path-only mandate can govern a command without making its participant an eligible workspace actor: when no steward or workspace participant resolves, the shared profile refuses every mode with `IA-RUNTIME-MANDATE-ACTOR`, even for one governing participant. The CLI's next command reads the workspace's governance position without writing. An owner may declare the workspace's steward or scope in authored source, then validate and rerun; `--actor` still accepts only the workspace's authored participants or steward. `tests/preview.test.ts` exercises both covers and participant fallback, the read-only refusal and next action, and success after an authored steward establishes the same actor.

### Administrative source boundary

`ia author` reserves `workspace`, `agent`, `mandate`, `system`, `schema`, `agent-profile` and `hook` records for administrative source edits. New records, `--set` (including list additions) and `--relate` all refuse with `IA-CLI-EDIT-AUTHORITY` (exit 1), after existing profile, ownership and candidate guards. The refusal names a read-only `ia position` command, says that an owner must make the change in source and validate it, and writes nothing. The existing `IA-CLI-EDIT-MANDATE` refusal still takes precedence for a mandate that binds the actor. `--actor` and an unrestricted or absent mandate do not bypass this boundary. `ia preview` remains read-only and retains its existing mandate guard; a successful administrative preview grants no write authority.

This conservative boundary prevents changing participant moves, exclusions, scope or covers, creating an alternate participant, replacing a default actor, changing the workspace's source closure, altering the admission vocabulary, remapping a host profile's actor, or weakening a hook through `ia author`. It intentionally refuses benign edits to the same words too, including `author system`, whose starter also creates an agent. It does not compute a rights-subset relation or introduce an opt-in field. Other words retain their normal authoring, admission and runtime checks; an operation or execution binding remains subject to its installed implementation and execution limits.

Owner migrations and grants are explicit source changes followed by `ia validate`; they can preserve existing identities, edges and locators without using `ia author`. These are cooperative tool restrictions, not authentication or filesystem isolation. Hand edits and host tools remain separate surfaces, and an owner should review the complete source change and its admission before resuming unattended work. Reverting this change restores the earlier CLI policy without migrating stored data.

`ia doctor` adds a read-only `source-protection` row. It warns when an authored mandate in the repository closure declares a restricted move, an excluded word or an execution limit and no supported authored hook explicitly covers the `.ia/src` tree for every `Write`, `Edit` and `MultiEdit` event. Full-tree declarations recognized conservatively are `.ia/src/**`, `.ia/src/`, `.ia/**`, `.ia/` and `**`; narrow or unsupported declarations do not silence the warning. Separate hooks may cover the tools together. The remedy names the governance position and describes an owner-authored `PreToolUse` hook; doctor neither writes a starter nor extends existing hook paths. No restriction or a complete declaration is `info`, never proof of enforcement. A complete declaration does not establish host registration or activation (Codex hooks remain unsupported); the current edit guard checks Synthesis on selected files, not word exclusions or operation limits on their bytes. Unreadable authority or refused mandate dependencies are `unknown`, as is a missing workspace or pending installation recovery.

## Host plugins

Host authoring (2026-10-14): a Claude, Codex or Grok plugin directory lowers into records, and a lowered workspace renders back into a plugin, with a check that the round trip is content-exact and a fixed point. The modules are workspace-runtime's `./internal/host-plugin` (inventory, frontmatter, lowering, manifests, comparison) and `./internal/generate`'s `renderPlugin` (workspace-runtime SPEC W05 and W06); `src/init.ts`, `src/plugin-sources.ts`, `src/plugin-product.ts` and `src/project.ts` hold the commands.

- `ia init [<directory>] --from <plugin-directory> [--id <provider/name>] [--apply] [--json] [--yes]` reads the plugin, relative to the directory the command runs in, and lowers it into the new workspace as a kit: the three starter records, then the system `<name>` (its `system.ia` requiring `agent-composition-system`, `agent-system`, `compliance-system`, `learning-system` and `workspace-system`, sorted, so authored trigger `@contract` and `@case` records and the `@observation` records of trigger evaluations can live beside the lowered ones, in the one system `--check` admits), `records/plugin.ia` (the product `@distribution`, one `@capability` per skill, and an `@agent`, a tools `@capability` and an `@agent-profile` per agent), every skill body, agent prompt and owned Markdown file byte for byte as a resource pinned in `.ia/authoring.resources.json`, every other file byte for byte as an asset under `assets/plugin/`, and `assets/lowering-map.json` (`ia.lowering-map.v1`) with `assets/MIGRATION.md` generated from it, giving every file and every frontmatter key one disposition. It plans by default and writes with `--apply`. `--from` conflicts with `--migrate`, `--adopt`, `--system` and the decline options. Lowering accepts only what `ia project --product plugin` writes back: an agent's `tools` must be one string whose `split(', ')` rejoins to exactly the original (a list, `Read,Grep` or a padded member is unresolved); each manifest must equal, by content, the manifest the renderer builds from the lowered product (`pluginManifest`), except that a Codex manifest may leave out the empty hook map; an explicit `disable-model-invocation: false` is unresolved, and its reason says to remove the key, because the renderer omits the default. The descriptor's `license` stays `UNLICENSED`, whatever the plugin's manifest states: the licence guard belongs to packing. The plan's apply command, the rerun an interruption names and the conflict refusal's next all carry `--from <plugin-directory>` as typed, so none of them initializes a plain starter instead. A target that is the plugin directory or lies inside it is refused before the plugin is read; a target that contains the plugin is legal.
- `ia project <claude|codex> --product plugin --out <directory> [--apply] [--json] [--yes]` renders the plugin into an absent or empty directory outside the workspace, create-only, after verifying each pinned resource; it plans by default. One plugin carries every host its product's `product.hosts` lists; the positional must still be `claude` or `codex`. Resources and assets are read only through real directories below the workspace root.
- `ia project <claude|codex> --product plugin --check [--compare <plugin-directory>] [--json]` renders in memory, compares each file with the original when `--compare` names it (identical, ruled by a named rule from `DIFF_RULES`, or drift, missing or extra), lowers the rendered plugin again and requires every lowered file, and nothing else under the plugin resources and assets, to match the workspace byte for byte (the fixed point). It writes nothing. `--compare` without `--check` is usage.

## Distribution commands

`pack --descriptor <file>` writes a digest-named archive, by default under `.ia/work/dist`. A release descriptor, as the database decodes it, that names no `distribution`, which a default `init` writes, is refused as `IA-CLI-CONFLICT` (exit 3), located at the descriptor, before the packer reads anything else, naming `ia vocabulary distribution`: a release needs a `@distribution` in a system folder whose identity the descriptor names, which `init --system` authors; a file that is no release descriptor is left to the packer's own refusal. `install`, `update` and `remove` preview a plan and apply it only with `--apply`; `--plan-out <file>` keeps the plan under `.ia/work/`. `restore --apply` reinstalls the locked generation from pinned archives; it has no preview, and `--allow-withdrawn` accepts a withdrawn release. Catalog, offline-cache and configured registry sources are explicit options. The native package IDs and versions in these commands are separate from npm package names and the CLI version.

`host <claude|codex|cursor>` previews a workspace registration and requires `--apply` to write it; `--remove` plans removal of the host set it owns. A workspace `--apply` writes the projection `ia project --apply` writes, so it is gated as the effect mode (Execution) by the acting participant's mandate profile before its confirmation, and takes `--actor <agent>`; its plan, `--remove` (which restores editing) and `--user` are not gated. For Claude, `--context <identity>` selects the lifecycle context element of a workspace registration, and `host claude --user` registers a user-level plugin that needs no workspace. `doctor` observes runtime, workspace, install and host state without repairing it or treating a written registration as an answering server; `--host` adds that host's session briefing and next actions. Unknown update or host observations stay unknown.

Installed implementations: `host <claude|codex> --apply`, `init --host` included, reads the join receipts before it writes anything, refusing ones it cannot read with the repair of deleting them, and once every element is applied records the host's join from the committed registration and the catalog of the payload it names; a removal drops it. A failure while recording names the rerun that finishes the set, so an interrupted apply leaves no join or the previous one. `doctor` adds an `implementations` row for the catalog of the payload this installation pins (`ok` present, `warn` when it lists an unavailable or revoked operation, `info` when the payload carries none or is not materialized, `fail` when the payload fails verification), a `join-<host>` row per recorded join, compared through the trust `validate` binds with: `ok` when it names the catalog of the payload this installation pins in the IA home and the host's registration names exactly that payload, `warn` when drifted, when the registration names another release or another directory (or another spelling of it, which is never opened) or the host is not registered, `unknown` when that payload cannot be read or verified or the installation pins none, an `info` row for a registered host with no join and a `fail` row for receipts that cannot be read; one verification of each payload serves its host, catalog and join rows, and doctor writes nothing. ## Automation and limits

`--help` and per-command help describe the accepted argument grammar. Consumer `--json` output is a single structured value without interactive prompts; applying without a terminal or with `--json` requires `--yes`. `--no-color` (or `NO_COLOR`), `--color`, `--ascii` and `--quiet` adjust human-readable output. Validation errors exit 1 (warnings alone exit 0), usage failures exit 2, unavailable inputs and local operational refusals exit 3, a remote registry or archive that `install`, `update` or `restore` cannot reach or read exits 4 (`IA-DIST-ARTIFACT-UNAVAILABLE`, or a remote `IA-DIST-LIMIT-EXCEEDED`), and interruption exits 130. Automation should inspect the structured diagnostic code and exit value together.

Every consumer refusal names one next command. With `--json` a refusal is `{version: 1, ok: false, code, message, exit, where, next}` and `next` is always a non-empty string; human output prints the same text on the `→` line, where the command it quotes is never broken across lines and runs past the line width when it must. The text quotes exactly one command and spells no other command or option outside it. That command is `ia …`, except that a recovery or a directory registry repair names `ia-distribution …`, the binary of `@inventarch/distribution`; a global install of `@inventarch/cli` does not put that binary on `PATH`, so such a command runs only where `@inventarch/distribution` is installed as well. The command carries the values this invocation supplied that it needs, such as the root (`ia init`'s `<directory>` included), the host, the package ids, the registry or catalog source, the descriptor or `--force`, so it runs from the directory the refused command ran in. Except where an unknown or interrupted command keeps the invocation as typed (below), a command that reruns the refused one repeats no output flag such as `--json` or `--quiet`, and one that runs the refused `ia install` or `ia update` again names its plan, without `--apply`: the plan applies nothing, although acquiring may fill the archive cache and `--plan-out` writes the plan file. A rerun of `ia restore`, which has no preview, carries `--apply --yes`; the rerun after deleting a cached archive drops `--offline`, so the archive is fetched again. A placeholder such as `<directory>`, `<path>`, `<file>` or `<url|dir>` stands only for the value the user has to correct or supply. A manual step the CLI cannot take, such as deleting or moving a named file, replacing a link under `.ia/src`, mapping a provider in `.ia/registries.json` or setting `IA_HOME`, may come first, and an explanation may follow. An unknown command names the nearest one with the rest of the invocation as typed, keeping only `--root` and `--params` for a machine operation. A workspace whose sources cannot be read (a link or alias under `.ia/src`, a source that changed during the read) names that repair and then `ia validate` with that root, which confirms the workspace opens. A service refusal that carries no next action of its own names the refused command's `--help` for a usage error, `ia validate` for a record finding (`IA-COMP-*`, `IA-GRAPH-*`, `IA-LANG-*`) and `ia doctor` for any other code, each with the root the invocation gave: its `--root`, or `ia init`'s `<directory>`. An interrupted command (`IA-CLI-INTERRUPTED`, exit 130) carries `next` in its JSON object and on its one stderr line: the rerun that finishes work already written, or otherwise the same invocation as typed, with any `--apply`, `--yes` and `--json` it was given. A file the invocation named that is not there (a `--descriptor`, `--catalog` or `--requests` file) names the same command with that one value as `<file>`. The machine protocol below is unchanged; its failures are the door's own one-line JSON and carry no `next`, so "every refusal names one next command" holds for the consumer commands. `@inventarch/cli/internal/consumer` keeps its 1.x forms: the `Refusal` constructor's `where` and `next` default to null, `refusalOf(error)` without the refused invocation returns a null `next` as before, and `renderRefusal` gives a refusal without a next action the fallback above, so `--json` `next` is always a string; every construction site in this CLI names its next action, which its tests enforce. `PlanRequest.reruns` in `@inventarch/cli/internal/distribute` is optional, and without it a plan's remedies are spelled from the request.

When a suggested root is omitted because it contains shell syntax, registry-consuming advice preserves the directory that a relative registry flag or inherited IA_REGISTRY selected from the original caller directory. The printed command uses a safe absolute spelling, or an equivalent safe relative spelling from the omitted root's destination. Explicit source-reselection remedies retain that intent; catalog and offline suggestions do not acquire an unused registry flag. Doctor has no registry flag, so a relocated doctor suggestion instead names its help and the exact original registry location to restore through the environment. If neither registry spelling is inert, the whole operation is likewise replaced by help and manual restoration guidance. Mere Windows separator normalization, an unchanged working directory, root-relative catalog/request/plan paths, actual parsed arguments, machine plan data and structured action argv keep their existing meaning.
The machine protocol, version 1, serves `scope`, `context`, `select`, `get`, `records`, `resolve`, `search`, `traverse` and `report`. Protocol version 2 appends `read`, `next` and `position`, which the runtime Door and the MCP door (`ia_read`, `ia_next`, `ia_position`) serve; `read`, `next` and `position` are the consumer verbs `ia read`, which returns the Door's body and digest and refuses a document the Door refuses with the same code, `ia next`, which prints the Door's delivery view, and `ia position`, which prints the Door's position, never machine routes, so the nine routes, their usage, help and schema, which still describe them at version 1, are unchanged; handed a later row, the published `@inventarch/cli/internal/operation-help` renderers describe it at its `paramsSince` revision when present, otherwise the version its `since` names. Protocol version 3 adds an optional `primitive` to `position`, preserving version 2 behavior when omitted and the original parameter whitelist on an explicitly version 2 Door. The machine routes open the Door at protocol version 1, so `read`, `next` and `position` through `runCli`, which `@inventarch/cli/internal/main` exports and the host launcher's `door` mode calls, are refused as the unknown operation 1.1.0 refused, byte for byte. Each takes its JSON parameters through `--params <JSON>`, or `--params -` for stdin, and prints one JSON line without color. `ia <operation> --help` lists an operation's parameters, refusals with their exit values, and an example; `ia <operation> --schema` prints its parameter schema. Scope tokens last for one invocation. These read operations do not invoke a model or grant host permissions. Only the CLI serves `report`; the MCP door does not. Generic structural validation does not attest evidence or execute a declared check.

Commands that start another program (`git` for `init` and `doctor`, `claude` for `host claude --user`) look it up only on fully qualified `PATH` entries and run it by absolute path from the user's home directory. An empty or relative entry, which would name the working directory, is never searched.

## Mandate authority

A `@mandate` may declare its authority as closed moves. Each mandate mode maps to one kernel move: read → Observation, validate → Verification, author → Synthesis, effect → Execution, re-seat → Delegation. The runtime publishes this table as `MODE_MOVES` beside `mandateRefusal`. The modes are not commands; a command's catalog row names its mode. `mandateRefusal` refuses a mode whose move the mandate does not list (`IA-RUNTIME-MANDATE-MOVE`) or a word the mandate excludes (`IA-RUNTIME-MANDATE-WORD`) and names `ia inspect <mandate> --edges both` as the next command. A mandate without `authority.moves` restricts no move, a declared list names at least one move, excluded words are refused whatever the moves, and a mandate adds closed restrictions only; it never grants host permissions. These commands are gated by the acting participant's mandate profile: `ia read` and `ia next` (read, Observation), `ia validate` and `ia preview` (validate, Verification), `ia author` (author, Synthesis), and `ia capture`, `ia project` and a workspace `ia host <host> --apply` (effect, Execution); a capture or project plan is judged as the effect it plans, and a host plan, `--remove` or `--user` is not judged. `ia position` is not gated, and neither is any other command or surface: the Door's read, next and position operations (the MCP tools), the install, update and remove projection refresh, `ia-distribution validate`, `ia inspect` and the records route, `ia init`, and `ia host`'s plan, `--remove` and `--user`; a mandate restricts only the gated CLI commands. Each gated command takes `--actor <agent>`, a canonical identity, `@agent <name>` or a bare name, which must be an authored participant of the repository's `@workspace` (an authored `@agent` a mandate scoped to it names as its participant, or its `composition.steward` when that is an authored `@agent`: runtime `defaultActor`'s `actors`); without it the actor is the workspace's default (runtime `defaultActor`, the answer the edit guard reads too), where an installed steward counts for no one and the participants decide. Naming an actor is a local declaration, not authentication: it is accepted whether or not the workspace leaves the choice open (it resolves the choice a workspace with several participants and no steward leaves, and under a steward it acts as another of the workspace's actors), and then that participant's own mandates are judged, which may be looser or stricter than the default actor's; it never lifts a move or excluded word those mandates state. The governing mandates (runtime `governingMandates` for the workspace and, for preview and author, the target file's path) are judged by `profileRefusal` for the mode's move and, for preview and author only, the word; the refusal (`IA-RUNTIME-MANDATE-MOVE`, `-WORD` or `-ACTOR`, exit 1) names the governance position of the mandate concerned; an open actor choice, or a default actor no governing mandate binds, names the same command with `--actor` naming the first participant whose mandates allow it (an `ia author` form whose `--digest` is absent or malformed names its preview form instead, which prints the digest, and the participant must be allowed that preview too), else the workspace's governance position; an `--actor` that names no participant names the same command without it where the default actor may run it (for an `ia author` form without a usable `--digest`, its preview form, which the default actor must be allowed too), else the governance position, and only under an open choice the first allowed participant. An admitted governing mandate whose authority the runtime cannot read, such as one with a child under `authority.moves`, which admission accepts, refuses with `IA-RUNTIME-REQUEST-INVALID` located at it (`where` `{path, line, identity}`) and naming that mandate's governance position. While an authored `@mandate` fails admission (2026-10-12; runtime R23), a stated `authority.moves []` among them since compliance C05 refuses it, every gated mode fails closed, workspace-wide, whatever the actor, the path or the word: it refuses with `IA-RUNTIME-REQUEST-INVALID`, exit 1, a `where` of `{path, line, identity?}` at the first such record (its identity when admission or spec 3.1 names one), and a message naming the record and its admission finding and saying a hand edit corrects it, since `ia preview` and `ia author` cannot target a record admission refused. The same holds, with the same shape, while a record an admitted mandate depends on fails admission (runtime R23): a refused `@agent` a mandate's `authority.participant` or a workspace's `composition.steward` names, or a refused `@workspace` a mandate's `authority.scope` names; `where` then locates the refused record and the message names the mandate or workspace that depends on it, while a refused `@agent` or `@workspace` nothing names, or a reference no authored record answers, restricts as before. Its next command is the admission report, `ia report --root <root>`, the version 1 machine route, which no mandate gates and whose findings show the record's: it runs for the same actor in the same state (exit 1 for a failing report, the report on stdout, nothing on stderr), where `ia validate` is gated and `ia position --seat <mandate>` cannot seat at a record admission refused. That route opens its `--root` or the working directory, never an ancestor, so the command carries the invocation's `--root` as every next command repeats it, or, without one, the root spelled relative to the working directory, `.` or `..` segments only, inert by construction, printed only when that spelling, resolved against the working directory as the route resolves `--root` (lexically, then to its real path), reaches this same real root: the spelling relative to the working directory as given, which on win32 keeps a junction's spelling, is tried first, then the one relative to the working directory's real path, so a junction or directory symlink in the working directory's path names a root that runs; where neither does, the command is `ia report`, run from the workspace root, with no path printed, so neither a root's shell-active characters nor the `ia preview <word>` substitution for a non-inert value reach it. The runtime locates the record as data (`RuntimeError.where`) and marks the refusal's cause (`isAdmissionRefusal`), which the CLI branches on, so a refused authored mandate that shares its identity with an admitted one of another band names the report and the hand edit too; the CLI parses no message for either. ## Path selections

A path selection is the text a record states to claim locations: `covers` on a `@mandate` (`authority.covers`), a `@law` or `@convention` (`subject.covers`), a `@spec` (`work.covers`) and a `@check` (`check.covers`), and `paths` on a `@hook`. A `@check`'s `check.scope` stays text that selects the verdicts the check binds to (the whole-workspace token `*`, a scope its evaluator reports, or prose) and is never a path selection, so it claims no location. These are the glob semantics every consumer of a location seat reads (db SPEC D02b). A selection is a workspace-relative path whose segments are separated by `/`, and a `\` reads as `/` in both the selection and the path matched. `**` as a whole segment matches any number of segments, none included; `*` matches any run of characters within one segment; `?` matches exactly one character; every other character matches itself, case-sensitively. A trailing `/` selects the directory and everything below it, so `docs/` and `docs/**` select `docs` and `docs/guide.md`; a selection without wildcards selects exactly that path. Braces, character classes, escapes and negation are not part of the dialect, and a leading dot is not special. An empty or absolute selection, or one with an empty, `.` or `..` segment, selects nothing, and nothing selects a path that is absolute or escapes the workspace. The graph package implements the dialect (`selects`, graph SPEC G06c), and the database resolves a path to the seat it is declared at and its claimants with it (`resolveSeat`, db SPEC D02b). No command in this release resolves a path to its seat; `read`'s `<path>:<line>` names the record that spans a line of an admitted source, not a seat.

Package tests cover parsing, JSON output, initialization and recovery, workspace inspection and formatting, distribution planning/application, host registration, installation and recovery, and the program lookup above. Repository qualification separately exercises built and installed artifacts. External registry publication and each host's own runtime behavior require separate evidence.

## Migration recovery and portability

This section completes the `init --migrate` row of the command table. `init --migrate` refuses edited legacy workspace or distribution text before writing: stock text with a changed `composition.systems` list is supported, but authored prose, answers, comments, relationships and distribution customization require an explicit authored migration. Plan lists the exact conflicting file; apply leaves its bytes intact. Kept records whose fields or relationships reference the local system, steward or distribution that plain migration would delete are conflicts naming both identities and the source file; `--system` retains those identities. Stock deletion without `--system` remains intentional.

Before any migration mutation, `migration-journal.ts` writes `.ia/migration.json`, an operation record bound to the absolute root, `--system` choice and exact bundled base. It holds the original plan, exact before/after file bytes and SHA-256 digests, directory removals and a durable cursor. Plan and resume verify the journal schema and digest, all completed states and pending preconditions before writes; only the cursor operation may already match its after state, covering termination between mutation and cursor publication. Edited destinations, corrupt journal data, changed flags, links and mismatched base refuse. Every file operation rechecks these states. The journal records initial host receipt digests and exact planned removal digests. A migrated receipt is recovered only when its render fields, current file digests, removed files and guard outcome match the plan; completed receipt digests prevent a later edit from being adopted, and successful receipts are preserved on resume. The journal survives descriptor, admission, capture and projection; file/effect interruption names the same migration apply command, with host transaction recovery first when required. A successful migration clears the journal only after all effects complete. Admission errors still require repairing the findings before the migration can finish. No rollback or adoption of matching files without the operation journal is implied.

When a migration creates `.ia/.gitignore`, tracked distribution payload stays visible to Git: it omits `distributions/` when `.ia/distributions` is already tracked. It never removes files from Git's index and preserves an existing ignore file. Before mutation a tracked installation whose existing ignore rules would hide new generations is refused with the rule to repair; inability to verify Git state in a checkout also refuses. A tracked installation whose effective Git attributes, filters, encoding or CRLF configuration could rewrite immutable bytes is refused with a scoped `.gitattributes` remedy for `.ia/distributions/**` and `.ia/distributions.lock.json`; existing attributes and Git configuration are never rewritten.

`bundled-base.ts` is the shared exact archive reader for init and restore. Restore can acquire the CLI's bundled base without network or a prepopulated cache when the lock matches its package identity, version, archive digest and manifest digest. The reader verifies archive bytes and embedded manifest before caching. Existing corrupt immutable cache content and locked manifest/version mismatches refuse. Other archives keep the existing acquisition rules. An exact unpublished bundled pin is exempt from registry lookup through the existing cached-unpublished rule, online and offline alike.

An already-initialized init target names `ia position --root <directory>` in the plan's text and JSON `next` and the apply refusal; a missing authored workspace asks for restoring that file from source control first. The catalog describes the already-initialized refusal and names `ia position --root <directory>`; conflicting files still use init's plan and repair.

The missing-authored-workspace refusal of `capture` also distinguishes an initialized root by its release descriptor: restore its authored source from source control, then inspect it with `ia position`; it does not route that case through init.

The migration Git preflight enumerates every exact prospective store file from the verified bundled archive or locked manifests, and computes the exact generation directory and its lock, inputs and optional workspace files. Ignore and conversion checks receive this complete path inventory through bounded NUL-delimited Git stdin, so selective directory, filename and extension rules cannot bypass synthetic probes. Refusals preserve existing ignore files, attributes and Git index.

Migration projection receipts include verified pending apply evidence when an earlier projection already retired the guard or removed stewards. An owned path already absent at migration start contributes no invented deletion digest. Completed projections are verified against their receipt and ownership state before reuse; if a repaired capture changes only their rendered host notes, migration refreshes them with the original retirement and removal evidence. The journal reopens that host effect before refresh, and the normal pending receipt preserves evidence through another interruption. User-modified projected bytes still refuse. Ordinary later projection applies keep last-apply receipt semantics.

CLI-only installation recovery: `ia recover [installation|host|guard|lifecycle] --root <directory>` delegates directly to the corresponding existing distribution recovery mechanism. The default mode is installation. The root is required and may be an incompletely initialized directory; recovery does not require source admission or an apply confirmation. Existing journal validation, rollback/forward selection, dead-lock cleanup and live-owner refusal remain the mechanisms' decisions. CLI refusals and doctor remedies use this installed `ia` route, including quoted paths with spaces, rather than assuming a transitive dependency exposes `ia-distribution` on PATH. The bridge has no position-packet catalog tag and does not change the frozen machine routes.

Receipt preflight validates the nontruncating opened destination handle, its current pathname and directory ancestor identities before accepting it. A concurrent replacement, new hardlink or linked ancestor refuses before guard retirement; the probe closes its handle on success and failure and preserves Windows sharing-lock detection.

Registry collections add `ia adopt <id>[@range] [--registry <base>]`, `ia init --adopt <id>[@range]`, and kit expansion for `ia install`. All retain preview/apply confirmation semantics. Adoption mounts pinned, source-only native records at open band 50, updates the authored workspace source declaration, captures, and refreshes registered packet projections. `ia doctor` lists and verifies source mounts.
