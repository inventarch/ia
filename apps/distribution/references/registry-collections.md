# Registry collections and source adoption

The public `./registry` interface supports `index(id)` and `index('release', id)` for existing release indexes, `index('kit', id)` for `kits/<provider>/<name>/index.json`, and `index('workspace', id)` for `workspaces/<provider>/<name>/index.json`. The built-in Inventarch mapping is unchanged. Providers serve a credential-free HTTPS base or an explicit local directory. A missing index is an empty release list. The existing shared 256-read budget, 4 MiB document limit, bounded fetch, no redirects, and portable/link-free directory reads apply to every kind.

`ia.registry-kit.v1` contains `id` and `releases`; each release contains `version`, `withdrawn`, and `distributions` with ordinary `{id, range}` requests. `ia install <id>[@range]` treats an explicitly named id as a kit only when its release index is empty. Its members pass the existing resolution, archive integrity, native admission, install transaction and registered packet refresh. The lock pins the resulting distribution requests and exact archive closure, so restore stays offline-capable without kit metadata. Removing or updating a kit is performed on those explicit distribution requests; kits confer no implementation catalog, registry override, credential or host permission.

## Collection record

The lock is not changed to remember which collection an install expanded: a new lock key or entry kind would make every older CLI refuse the repository. Instead `.ia/kit-collections.json` (`./kit-collections`), committed beside the lock, keeps each collection's identity: `{"format": "ia-kit-collections-1", "lock": <sha256 of the lock bytes it describes>, "collections": [{id, version, registry, members: [{id, version, archive}]}], "unknown": [{id, members: [<member id>]}]}`. `registry` is the HTTPS URL or directory the kit index was read from. Every collection and member id is a distribution id (`provider/name`, the lock's rule); a record holding any other id is unreadable, so an id such as `--root=/other` never reaches a fix doctor offers. Rows and members are sorted by id. A kit release that lists another kit expands it in turn, and the row of the collection the command named records the members that expansion reached in its place; a kit reached that way gets no row of its own. A row is built by joining each member id of the expanded kit release to the resolved plan lock's `packages` row of that id, for its exact version and archive; a member the lock lacks refuses with `IA-DIST-INSTALL-COLLECTION-MISMATCH` before `pending.json` is written, so the lock, the record and the activation stay as they were (the preview, which runs the same merge to name the record in its "Would write", refuses the same way). A record left with no collection and no unknown entry is removed rather than written empty.

Every apply (`install`, `update`, `remove`, `restore`) merges the record inside its installation lock: it starts from the record that describes the lock before the operation (from none when it describes another), drops the rows of each collection the operation expanded, keeps every other row only while all its members are the new lock's exact pins (a row with any member removed, re-pinned or re-archived is removed whole, so its other members can never make it intact again), and adds the expanded rows. An unknown entry stays until its collection is installed again or none of its members is left in the lock. A restore of an unchanged lock writes nothing. A record file that cannot be decoded (not JSON, a member id that is not a package id, another format) is never treated as none: the apply refuses with `IA-DIST-COLLECTIONS-UNREADABLE` before it writes any store, generation, lock or record file (through `ia`, after the plan, which may already have filled the archive cache or written `--plan-out`), naming the file and its reason, since the merge would replace it and lose its collection rows (the installed packages stay; with no lock yet, as in the install `ia init` makes, the refusal says instead that nothing installed is at stake). The same holds for a record in a format this ia does not know, such as one a newer ia wrote: every apply refuses it, `ia init` included, and the file is left exactly as it was. The remedy is to restore the file from version control or a backup, to move it aside if its collections may be forgotten, or, for an unknown format, to upgrade ia, and run the command again.

While an apply changes the record, a journal in the local install state, `.ia/distributions/kit-collections.journal.json` (`{formatVersion: 1, beforeActive, afterActive, before, after}`: the exact activation pointer bytes before and after, and the record's bytes before and after, `null` for none), binds the change to the activation it belongs to. The write order is: `pending.json`; the journal (checkpoint `collections-journal`); the record (`collections`); the lock; the activation pointer; the journal removed (`collections-journal-removed`); `pending.json` removed. `ia recover installation` writes the record as `after` when the activation committed and as `before` when it rolls back, then removes the journal, before it removes `pending.json`. The activation pointer carries no transaction nonce, because its decoder refuses any extra key and older readers would refuse the workspace's `active.json`.

Which record counts, read only and failing closed: with a journal and `pending.json`, an operation was interrupted, so no collection identity is reported ("installation interrupted; run ia recover"). With a journal and no `pending.json` (a recovery that did not read the journal), its `after` counts while `active.json` is exactly `afterActive`, its `before` while exactly `beforeActive`, and otherwise the collections both sides agree on byte for byte, every other one unknown with the member ids either side recorded; the next apply settles the record that way and removes the journal. With no journal, the record file counts. The chosen record counts only when its `lock` is the sha256 of the current lock bytes, and inside it a collection is intact only while every member is the lock's exact pin; otherwise its members are inventoried as plain releases and the source is reported unknown, never guessed. A reader takes the record and the lock between two probes of `pending.json`, the journal, the activation pointer, the lock and the record, by content and by file identity (inode, modification time and size, so a file put back with identical bytes still counts as a change; where no inode is reported, the time, size and content stand alone); when another process changed any of them in between, it reads once more, and when they change again it reports every collection the record or journal names as unknown. One residual case is accepted: when an older CLI rolls back a staged collection upgrade whose lock is byte-identical and then restores the unchanged lock, it recreates `afterActive` exactly, and the upgraded version is reported although it never committed; the pins and archives are the same either way, and the next install or update of the collection corrects the version. A second residual is accepted too: on a volume that reports no inode and whose timestamps do not move between a reader's two probes, a rollback that restores identical bytes between them goes unseen, so that one read may report the staged version. It changes nothing on disk, and the next read reports what holds.

Re-installing a collection replaces the member requests its earlier expansion left (both sides' members for an unknown one): they leave the requests before the new release's members are added, so a member whose range changed is not a conflict, and a member the new release no longer lists stays locked only while something depends on it. A member request the same command names itself, that another collection expanded in the same command introduced, or that another installed collection still lists (unless the same command expands that collection too), is kept, so it conflicts as any other direct request does: two collections upgraded together never overwrite each other's member constraints, and re-installing one collection never drops a member another installed collection lists, nor that collection's row. Ranges are compared as strings, not intersected: when the new release lists such a member with another range than the one the other collection left, the install refuses with `IA-DIST-CONFLICT`, naming that member, each collection that still lists it and the range it left, and its next command installs the collection together with them (`ia install <collection> <other>`), which re-expands both and succeeds only when their releases list the member with the same range. `./kit-inventory`'s `installedUnits(root)` lists what `ia install` and `ia update` can move: each lock `package` entry, each intact collection, and each remaining direct request, with that source.

`ia.registry-workspace.v1` contains `id` and `releases`; each release contains `version`, `withdrawn`, `revision`, and `files` with `{path, text}`. It is source data, with at most 1,000 files, 1 MiB per file and 3 MiB of combined text. Native paths must be under `.ia/src`, outside its floor; documentation is explicit portable `.md` or `.txt` paths outside hidden roots. The revision is SHA-256 of the stable serialization of the sorted native `{path,text}` rows. The source parser checks every native file and refuses authority-producing `mandate`, `agent-profile`, `execution-binding`, `hook`, `capability`, and `check` records, including nested records. Author and review those records locally. No executable, host configuration, registry mapping, implementation catalog or remote credential is copied or loaded.

`ia adopt <id>[@range] --registry <base>` previews by default. `--apply --yes` writes `.ia/open/.gitattributes` with `* -text -filter -ident -working-tree-encoding` unless a regular file is already there, which keeps checkouts from converting pinned bytes unless a higher-precedence git attribute says otherwise, pins a source tree at `.ia/open/<binding-id>/<revision>`, records a version-1 `.ia/workspace.json` `open` binding, and adds `<tree>/.ia/src @open` to the sole authored workspace's `composition.sources`. These records enter at band 50, below installed/adopted band 90 and authored band 100. Binding IDs are deterministic hashes of the provider-qualified id; identities, edges and native bytes are unchanged. Existing local `adopted` bindings keep their version-1 behavior. The planner checks candidate admission and any existing destination entries before writes. Native paths excluded by physical source discovery (`dist`, `node_modules`, `.git`, and the floor) are refused. Apply verifies exact destination file membership and bytes, then checks the physical native revision before publishing the declaration or binding; unlisted owner data is preserved and causes refusal. Apply holds an exclusive adoption lock, rechecks the inputs, writes immutable mount files, then updates the declaration and binding. A manifest-write failure restores the declaration when it still holds this operation's bytes. After a process crash, inspect the declaration and binding before removing the stale `.ia/adoption.lock`; no automatic crash recovery is claimed. Unreferenced immutable files may remain after interruption; the published source set does not include them. Capture and registered packet refresh follow publication; their failure explicitly reports that adoption already applied and prints one adoption retry pinned to the selected version, preserving the root and explicit registry. After repairing the reported failure, that retry completes capture and registered projections. A repeated application of the same pin is safe; a different revision requires explicit removal of the old binding first.

`ia init --adopt <id>[@range] [--registry <base>]` includes the selected source-only adoption in its preview, then installs the bundled language, pins the mount, authors the starter including its source declaration, admits, captures, and projects. Existing bindings are reflected in the starter even without `--adopt`. `ia doctor` verifies pinned source bytes and lists each mount and placement. Reading and captured-resource resolution preserve the open mount's source locator and revision; they do not create execution authority.

For rollback, remove the exact open binding and its matching authored `composition.sources` entry, then run `ia capture` and `ia project <host> --apply --yes` for each registered host. Keep the immutable tree until no retained capture needs it. No install or adoption operation publishes a release.

`registryAddCollection(dir, kind, index)` validates and writes directory-registry kit/workspace indexes, refusing removal or mutation of an already listed version. `tools/release/distribution.mjs <directory> <output>` reads an explicitly authored `.ia/kit.json` with `systems`, `descriptor`, and `assets` (and an optional `kit` index), then uses the public language dependency closure to pack exactly the selected owned systems. The output is local package artifacts and optional kit metadata; publishing its dependency closure and release indexes uses the existing reviewed registry builder. The exported `packOptionalDistribution(root, options)` also accepts already-selected asset bytes. The product-structure wrapper keeps its reviewed assets/resources and delegates packing to that common implementation.
