# @inventarch/distribution

Public language mechanism. The [language reference](LANGUAGE.md) defines vocabulary and evaluation limits. Package exports describe the installed API. Curated agent methods and hosted services are supplied independently.

The [installed system-package API](references/system-package.md) verifies explicit per-system native ownership and exact selected dependencies without executing package code.

Verified reads (2026-10-16): the host launcher's cache walk (`assets/host-launcher.mjs`, which every launcher mode runs first), `installedDistributionDigest` (`./inventory`) and `verifySystemPackage` judge each file by the descriptor they read it through. Each opens a file before it is judged, never through a final link where the platform refuses one at the open and never waiting on a FIFO; its type, its size and, for the launcher, its link count come from that descriptor; the read stops one byte past that size; and afterwards its name must still hold that file. On Windows the open has neither guard, so a link swapped in after the listing is opened and read, and that last check refuses it. The runtime inventory and the package reader refuse a file of more than 2147483647 bytes, the most `readFileSync` reads, before reading it, the inventory with its one message and the package reader as `System package input exceeds 2147483647 bytes: <path>`; the launcher reads only a pinned file within its 256 MiB budget.

The launcher judges every entry not listed as a regular file by its lstat, as it judged every entry before, since Windows lists every reparse point as a link: a link or a special file refuses before anything is opened, a directory is walked, and an entry its lstat calls a file or a directory, such as a cloud placeholder or a deduplicated file, is judged as that. It refuses a link (`Plugin cache links are unsupported`), a special file or a file with a second link, the files it skips included (`Plugin cache file is aliased`), and an unpinned, resized, over-budget or changed file (`Plugin cache payload differs: <path>`). An entry its listed name no longer reaches, removed once it was listed or listed under a name that is not UTF-8, which Node decodes lossily on Linux, is never admitted: a pinned one is missing (`Plugin cache payload is missing`), and any other, a directory or a file the walk would skip included, refuses as `Plugin cache payload differs: <path>`. Of the failures that keep a file from opening, only that of a pinned file the walk may not read (EACCES, EPERM) prints the system's error; any other leaves the file to be judged by its name, and a pinned file that still failed to open refuses as `Plugin cache payload differs: <path>`. An entry it can list but not lstat, in a directory it can list but not enter, fails with the system's error, as before.

The runtime inventory judges every entry but a runtime file listed as a regular file by its lstat, as it judged every entry before, with the same consequences for a link, a special file, a directory and a reparse point. It admits hard links, and refuses a link, a special file, an entry its listed name no longer reaches, a file that changes while it is read and any open that fails, an unreadable file included, with its one message. An entry it can list but not lstat, in a directory it can list but not enter, fails with the system's error, as before, but for a runtime file, which it opens and so refuses with its one message.

The package reader (`verifySystemPackage`) refuses a link on the way by name before it opens the input. It admits store hard links; an input that is or becomes a link refuses as `System package input is aliased: <path>`, one that is no regular file as `System package input is not a regular file: <path>`, one whose name stops holding the file read or that changes while it is read as `System package input changed while it was read: <path>`, and a missing or unreadable input fails with the system's error, as before.

`packSnapshotSet` additionally accepts one root-authored release control at `.ia/src/releases/<distribution-name>.ia` per release. That file contains exactly the selected public `@distribution`, its meaning and its unconditional `@system` roots. The archive retains those exact source bytes and pins them; verification refuses extra records, relationships, nested declarations or roots differing from the manifest. Release roots still belong to native system folders, and whole selected systems remain the payload ownership unit. The installed generation loads the pinned control as an adopted root instance so direct distribution references continue to resolve. `packSnapshot` retains its existing native-folder declaration requirement.

Root release controls separate publication selection from vocabulary ownership. They do not create dependencies on every system named by other release controls. Per-system packages explicitly depend on workspace-system for their release declaration and generated installation workspace vocabulary. Workspace-system therefore keeps its agent/compliance foundation closure; generated teaching guides retain their actual schema dependencies. Native and npm versions remain independently selected.

Packing (since 2026-10-09) refuses a release descriptor that names no `distribution`, which the database's descriptor decoder admits for a workspace that releases nothing, as `IA-DIST-CLOSURE-INVALID` as soon as it decodes the descriptor, after it verifies the snapshot's sources and before it admits them, computes the release closure or writes anything; a descriptor that names one packs as before.

The host projection mechanism (`./projection`; 2026-10-09) plans and applies the files a caller renders, each carrying the marker the caller passes, at the exact `PROJECTION_PATHS` of each host: `.claude/rules/ia-workspace.md` and `.claude/skills/ia-authoring/SKILL.md` for Claude, `AGENTS.md` and `.agents/skills/ia-authoring/SKILL.md` for Codex, and the generated files `GENERATED_PATHS` names: `.claude/agents/<name>.md` and `.claude/skills/<name>/SKILL.md` for Claude, `.agents/skills/<name>/SKILL.md` for Codex, each a lower-case portable name (`projectionOwnable` is the union). A generated file carries the packet marker and is a planned write owned through the same state; an owned one no render writes any more is removed when it still carries an owned marker (an agent through the legacy path below, which deletes only a marked, unedited file; a listed skill without the marker is the user's, kept as `foreign` and dropped from the state), and the skill folder that removal empties is removed too, never recursively; a generated skill is refused (IA-DIST-LOCAL-MODIFICATION) where its folder already holds files and the state owns nothing in it, located at that folder and naming it as `skillFolder`, so the caller names the files to move, a user's own unmarked SKILL.md there included, so the refusal converges in one hop; the packet's own `ia-authoring` skill keeps the file rule; an unmarked or hand-edited file at a generated path is refused, never overwritten or removed; a generated agent is refused (IA-DIST-PATH-UNSAFE) where `.claude/agents` is a link. A generated agent at the path of an owned 1.x steward file replaces it as one update: the legacy pass skips every path an artifact writes, so no plan holds an update and a remove for one path. Besides the caller's marker, the two 1.x markers (`<!-- Generated by tools/projections/generate.ts; edit the cited native records. -->` and `<!-- Generated by ia host; edit the cited native records. -->`) are owned, so a file a 1.x renderer wrote is replaced in place rather than refused. The ownership state format `ia.host-projection-state.v1` is unchanged, and a Claude state may still list `.claude/agents/<name>.md`, for removal only: the planner plans `remove` for each listed one that carries an owned marker and is unedited (a listed one already gone only leaves the state), refuses a listed marked one edited by hand as it refuses any owned file, and lists every other agent file, a listed unmarked one and any the state does not list, marked or not, as `foreign`, which no apply writes or deletes. The final state lists only the files rendered. `observeProjection` reports no drift for a listed steward file that is gone or unmarked. The CLI's `applyHostProjection` is the one caller that applies these plans; the steward-guard registration it retires first is `./guard-registration`'s removal, with the safety checks below.

The installed-implementation catalog (`./implementations`) is the `implementations.json` file, format `ia.installed-implementations.v1`, that the host payload builder generates and inventories; the builder finds each first-party implementation package only in the repository's own `node_modules` and imports its declaration module at build time to read the declaration, which no host app ever imports. Its value's shape is `@inventarch/db/distribution`'s (`checkInstalledImplementations`), which binders read too: an `evaluators` section that is an `ia-evaluator-catalog/1.0` value with no installed entries (the built-ins are implicit), and an `operations` section listing each first-party installed operation implementation `available` (descriptor version, operation identity, handler, input and output validator ids, the payload path of its shipped handler module, that module's SHA-256 and the installed packages of its closure), `unavailable` or `revoked`, each with a reason. `readInstalledImplementations(directory, release, verify?)` first verifies the whole payload as `verifyHostCache` does (which now also returns the verified inventory) and requires it to verify as `release`, a release.json that does not hash to it refusing before it is parsed: a file anywhere in the payload directory that the inventory does not list (nothing outside that directory is verified), a link, a missing file or changed bytes refuse with that verification's code, so nothing is ever read, let alone available, from a payload that fails verification. The catalog is the file that verified inventory lists, read again against its pin; an available operation whose handler module or closure package manifest the inventory does not list is `unavailable`, and one whose handler digest disagrees with the inventory is `IA-DIST-INTEGRITY-MISMATCH`. What binds an implementation is its handler module's digest together with the verified inventory, which pins every other byte of its closure; the composition descriptor's own `implementationDigest`, which hashes the installed package trees of the process that imports it, is a producer-side pin the catalog does not record, and a bundled host's counterpart is the payload release digest a join records. A v1 payload, or a v2 payload whose inventory lists no catalog, reads as `unavailable`, not as damage. It never imports, loads or runs a handler. `joinHost(root, host, consumerRevision)` records, under the host lock and after a pending-journal check made under it, the host's row in `.ia/distributions/hosts/joins.json` (format `ia.host-joins.v1`: consumer, implementation `installed-implementations`, payload version, catalog digest, payload release, consumer revision), derived from the committed `<host>-workspace.json` registration and the catalog of the payload it names; with no registration or no catalog it drops that row instead. `leaveHost` drops a row; unreadable receipts refuse, located at the file, rather than being replaced.

Execution bindings: a catalog row may also be `revoked`, with a reason, which binders report as an error. `joinedCatalog(root, trust)` finds the catalog a workspace's host joined, as `trust` (`HostTrust`: the validating installation's IA home and the payload release it pins) allows. Only `<home>/hosts/<release>` is ever opened: a join counts only when it and its host's registration name that release and the registration names that payload directory, so a registration of another release, or of a payload anywhere else (another IA home, inside the workspace, a network path), is `unavailable` with the repair `ia host <host> --apply` and nothing it names is opened. That payload is read once; a payload that fails verification with changed or unlisted files, a link, exceeded limits or a release.json that does not hash to the pin (parseable or not) is `damaged`, whichever trusted join names it, since every trusted join names the same payload; otherwise the first trusted join in consumer order that carries the payload's catalog digest is the source. With no receipt, no trust (null) or no trusted join that holds, the catalog is `unavailable` with the reasons. `installationTrust()` is the trust of the distribution module's own installation: the payload it runs from, `<home>/hosts/<release>/runtime/node_modules/@inventarch/distribution`, or null outside one. `WorkspaceSession.bindings(trust)` joins every admitted `@execution-binding` with it (`@inventarch/workspace-runtime/bind`) and returns the catalog source and one result per binding; `ia-distribution validate` passes `installationTrust()`, adds that result as `bindings` and exits 1 when a binding is revoked. It reads only.

Check binding and evidence: `openWorkspaceSession({root, checks})` passes db `OpenOptions.checks`; every other caller keeps strict admission. `openWorkspaceSession({root, conformance: 'verify'})` passes db `OpenOptions.conformance` (db D10a), so the session's report verifies COMP-KERNEL and COMP-FIXTURES in-process; only the report changes. Because `checks()` and `recordValidation` bind from the session's report, a validation records its evidence from a session opened without the option. A session never reads evidence, so what a validation admits, binds and reports is the authored view's alone, and `validation()` reports `revision`, the one every other reader reports, and `authoredRevision`. `WorkspaceSession.checks(trust)` binds every admitted `@check` with db `bindChecks`, a catalog evaluator against the same catalog `bindings(trust)` reads (`joinedCatalog`, read once per session and trust), and returns the catalog source (null when every check names a built-in evaluator, and then no catalog is read) with one result per check; `validation()`, `bindings()` and `checks()` read only. `recordValidation(session, checks)` is the validate request and the one writer of evidence: it records the session's bound checks that passed or failed through db `evidenceText` and `writeEvidence` at the session's authored revision, reading the current file only for the times an unchanged observation keeps; nothing when the vocabulary has no `@observation` word, and nothing recorded or pruned when admission is refused. Only writing this revision's file can refuse: a directory or file the process cannot write as IA-DIST-EVIDENCE-UNWRITABLE, located at `.ia/work/evidence`, and a link or misplaced entry as db IA-DB-PATH-UNSAFE; pruning other revisions' files is best effort and keeps what was modified after the session opened. `ia-distribution validate` opens a structural session, adds `checks` and `evidence` to its result, and exits 1 when a binding or a check is revoked. Two trust roots: `ia validate` trusts the payload its bundled pin names in the IA home, while `ia-distribution validate` trusts only the payload it runs from (`installationTrust`); run from a package install or a checkout, outside any payload, it trusts no join, so its catalog is unavailable and no catalog check or execution binding binds where `ia validate` may bind them.


PR #30 upgrade safety: `assertRetirableGuard` inspects both Claude settings locations and refuses unmatched IA guard groups before a caller deletes steward files, preserving unrelated settings. Guard removal accepts a recorded old-root group only in the fixed released shape and only when the current group matches the recorded bytes; registration and execution retain strict current-root validation. A linked legacy agents directory is foreign and never traversed; listed paths beneath it are left untouched. `legacyProjectionActions` exposes removal/foreign actions independently of active files that an install refresh will render after activation.

Hook groups (`./guard-registration`; 2026-10-11): `planHookRegistration(root, {cache, hooks} | {remove})`, `planHooksFor(root, expected, hooks)` and `applyHookRegistration(plan, checkpoint?)` plan and apply exactly one PreToolUse group in `.claude/settings.local.json` per hook row `{identity, tools, paths}`: the matcher is `Write|Edit|MultiEdit` whatever the row's tools (which are validated and reported, and which the guard applies to the hook's paths from the record), so the guard's managed-state protection decides every edit tool, and the one handler runs the launcher's guard mode as `guard --root <root> --hook <identity>`, in the derivation the retired steward guard's group used (direct on win32, `/bin/sh` with `FAIL_CLOSED` elsewhere, timeout 10). Nothing authored but the identity, a canonical `system/kind/facet/name` of at most 512 characters, and the tools reaches a group. Rows are held to the bounds hook generation applies (workspace-runtime `HOOK_LIMIT`, `HOOK_SELECTION_LIMIT` and `registrableSelection`: at most 64 hooks, each with one to 64 selections of at most 512 characters), so a hook beyond them is reported by generation, never refused here. The groups are owned by exact match against `.ia/distributions/hosts/claude-hooks-<id>.json` (`ia.hook-registration-state.v1`), which also records each hook's registered `paths`, the selection the guard refuses when the hook's record can no longer be read: a plan replaces an owned group whose derivation changed in place, appends a new one, removes one no longer requested, and keeps every other group, key and byte, so a re-plan of the same rows writes nothing and removing the last hook restores the settings byte for byte, except that a container the groups emptied which existed before is written as `[]` or `{}` whatever whitespace it held (a file the first registration created goes again, and containers it created are pruned). It refuses an owned group changed or duplicated by hand, an unmanaged group identical to one it would write, `disableAllHooks` when it would create or update a group (a plan that only keeps or removes owned groups proceeds), a consumer root inside the cache, and a malformed or repeated row; an owned group the user deleted only loses its ownership when its hook is no longer requested. Publication holds the host lock and uses the guard's journal, `guard-pending.json` with format `ia.hook-registration-pending.v1`, which every host write already waits on and `recoverGuardRegistration` (`recover-guard`) finishes or rolls back. `assertRetirableGuard` and the retired guard's removal recognize only a guard group that names no `--hook`, so hook groups never block the projection apply's retirement of the steward guard's registration. `readHookRegistration(root)` reads the hook ownership state, `observeHookRegistration(root)` reports each owned group `missing`, `modified` (changed or duplicated) or `foreign` (a guard group naming `--hook` for this root that no state owns), read-only, and `hookGroupDigest(group)` is the SHA-256 a receipt lists for a group, and `hooksDisabledBy(root)` names the settings file whose `disableAllHooks: true` turns hooks off, read as registration reads it. The CLI's projection writer registers and removes the groups (apps/cli SPEC, the generated set).

Transport (`./internal/bounded-fetch`; 2026-10-16): `fetchBounded` is the one GET behind registry documents and remote archives, under the bounds of the [registry spec](../../docs/specs/registry/README.md) §5.1 and §6.4: redirects refused, a 30-second timeout joined to the caller's signal, declared and streamed bytes bounded. Whatever its caller checked, it parses the URL with `new URL` and refuses only a URL that does not parse, whose scheme is not `https:` or that has a username or password. That refusal comes before any request, as `IA-DIST-INPUT-INVALID` with the message `<label> <url> is not a credential-free HTTPS URL`. It then requests the canonical form `new URL` writes. A query or a fragment passes, and a legitimate non-canonical HTTPS spelling, such as an uppercase host (`https://Registry.test/ia-registry.json`), an explicit `:443`, a percent-encoded host character, an IPv4 number form, a dot segment or an empty userinfo, is canonicalized and still accepted; fetch makes the request it made before this check, when it was handed that spelling itself, so a direct caller passing an HTTPS URL sees no break. Before this check, an `http:` URL was requested in clear text and a `data:` or `blob:` URL was read in process; a URL with any other scheme, such as `file:`, `ftp:` or `wss:`, got a `TypeError` from fetch, reported as `IA-DIST-ARTIFACT-UNAVAILABLE` with the message `<label> <url> failed: …`, as a credentialed or malformed URL did. All of them now refuse as `IA-DIST-INPUT-INVALID`, so both the code and the message change. Refusing another scheme is a defensive patch, not a contract change: the supported contract already excluded it. The [registry spec](../../docs/specs/registry/README.md) says "A registry base is a credential-free HTTPS URL or a local directory" (§3) and "HTTPS bases must carry no credentials, query or fragment, and other URL schemes refuse" (§4), and the archive check admits only HTTPS artifact URLs. Messages name the URL as the caller spelled it. Every URL built on a base that `parseRegistryBase` returns, and every URL the archive check admits, is already canonical and is requested unchanged. To migrate, a direct caller, or one that builds its own `RegistryBase`, can keep passing HTTPS URLs, in any spelling, or call `parseRegistryBase` to get the canonical form up front; a direct caller passing an `http:`, `data:` or `blob:` URL moves to an HTTPS URL or, for a registry, a local directory base. This is URL-shape hygiene, not host authorization: it does not keep a request from internal or loopback hosts, and it does not prevent DNS rebinding or other server-side request forgery.

An installation plan whose lock requires an unsupported distribution engine refuses with `IA-DIST-CONFLICT`, naming its required range and the current installer engine. Installed reads distinguish `engine-incompatible` from corrupt state through the database error reason. Neither restore nor recovery upgrades the running implementation; no fallback rewrites a lock or lowers an archive engine range. The compatibility and rollback procedure is documented in [README.md](README.md).

Explicit hook removal checks both Claude settings files before making changes. `assertRemovableHooks` refuses an IA hook group without matching ownership, including after the ownership file is lost or a workspace is moved, at the settings file that contains it. Its `unownedHook` detail identifies that group for manual recovery. It never adopts or deletes an unowned group; other settings and owned state remain intact. The ordinary modified/duplicate owned-group checks still apply. An explicit removal cannot report success while such a group remains active.

The user-level plugin home (`./plugin-home`; lock judgment and owner-aware release 2026-10-16): `materializeMarketplace` holds `<IA home>/claude/.lock` from its recovery through its swap, and `removeMarketplace` for its whole removal. A run creates the lock exclusively, as a regular file holding its pid, a space and a random token of its own, and refuses `IA-DIST-INSTALL-BUSY`, naming the lock, while another run holds it; the pid comes first, so a reader that parses a leading pid, as earlier CLIs do, still finds it. An exclusive create refused with a busy code (on Windows, a lock name another run is still removing) is retried after waits that start at 1 millisecond and double to at most 50, each begun less than 250 milliseconds after the create's first try began; the create after each takeover attempt starts over. A busy refusal after those 250 milliseconds is judged like any held lock while a file holds the name, and with nothing there the create is tried once more; one still refused with nothing at the name, or refused with a permission code off Windows, refuses `IA-DIST-INPUT-INVALID`, naming the directory. A held lock is judged through one descriptor, opened without waiting on a FIFO and, where the platform can refuse one, without following a symbolic link, so its type, age and pid are those of one file. It is taken over only when it is a regular file whose pid parsed as an integer from 1 to 2147483647 and is not running, or is running but the lock is older than a day, or whose pid is empty, unparseable, 0 or negative, or above 2147483647 and that is older than 10 seconds (none of these names one owner: on POSIX the liveness check takes 0 and a negative number for a process group or every process, on Windows 0 is the caller itself, and Node refuses a larger number on every platform), and it is removed only once its name is found, while that descriptor is open, to still name the judged file. A lock whose pid is running is judged stale only once it is older than a day: a run holds its lock for milliseconds, so a younger age does not show that its owner stopped, while a day-old lock whose pid is running belongs to a process that reused a dead owner's pid, to one that answers EPERM, or to a run frozen in its hold. Until then such a lock stays busy unless it is removed by hand, as the refusal says to do when no run is active. Liveness is judged in the judging run's own pid namespace, so a run in another pid namespace sharing the IA home, such as one in a container or on another host, can find a live run's pid not running and take its lock over. A symbolic link, any other non-regular file and a lock the run cannot open are never taken over, so each refuses `IA-DIST-INSTALL-BUSY`, as does a lock that keeps coming back after five takeover attempts. A hard link at the lock path names the judged file itself, so it is judged like any other lock, and taking it over removes only that name. A run releases the lock only while it is still its own: a regular file, judged through one descriptor opened the same way, that holds exactly the pid and token the run wrote and whose name is found, while that descriptor is open, to still name it. Any other lock at the path (another run's token, an earlier CLI's pid alone, a symbolic link or any other non-regular file) and one the run cannot open or read are left in place, and the release never fails the run. A takeover removes a stale lock only under a claim on the judged file: an exclusive directory beside the lock, named `.lock.<inode>.claim`, made while the descriptor is open, after which the lock's name is compared with the judged file again. Two runs on one host that judged the same stale lock therefore never both remove it, and a lock another run created after this run's judgment is left in place. A claim older than 10 seconds is abandoned and removed, and a run that acquires the lock sweeps abandoned claims beside it. Between each final comparison and its removal a window remains, as Node has no unlink-if-same, and the removal takes whatever the name holds by then; only something that removes the lock without the claim can change it there: a hand, an earlier CLI (which never claims), or a run whose claim was removed as abandoned, because it froze inside it for longer than 10 seconds or because two runs removing an abandoned claim interleaved. In a release, a run in another pid namespace sharing the IA home, which judges the run's pid not running, can also replace the run's lock, and such a replacement is then removed. Earlier CLIs sharing the IA home also release their lock unconditionally, removing whatever lock is at the path, so two runs of this CLI can still overlap until every CLI using that home is upgraded.

Payload verification within one command: `hostVerifier()` (`./host-observe`) memoizes `verifyHostCache` per directory, and only a verifier `hostVerifier` made counts as one (`host-verdict.ts`, which is no package export), so no caller can stand in for verification. `materializeHostPayload({ …, verify })`, `planHost(root, host, cache, removeId, verify)` and `planHookRegistration(root, request, verify)` take a command's shared verifier and reuse the verdict it holds; with none, or with any other function, each verifies afresh, as before. A verdict is never reused across a write to that directory: `materializeHostPayload` verifies the stage it writes afresh and records the target's verdict only after its last write there. Every check that guards a commit verifies afresh: `applyHost` and `applyHookRegistration` re-plan under the host lock without a shared verifier, and their checks before activation and commit call `verifyHostCache` directly. Thus a payload that changes after a command's plans still refuses its apply.
