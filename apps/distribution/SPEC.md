# @inventarch/distribution

Public language mechanism. The [language reference](LANGUAGE.md) defines vocabulary and evaluation limits. Package exports describe the installed API. Curated agent methods and hosted services are supplied independently.

The [installed system-package API](references/system-package.md) verifies explicit per-system native ownership and exact selected dependencies without executing package code.

`packSnapshotSet` additionally accepts one root-authored release control at `.ia/src/releases/<distribution-name>.ia` per release. That file contains exactly the selected public `@distribution`, its meaning and its unconditional `@system` roots. The archive retains those exact source bytes and pins them; verification refuses extra records, relationships, nested declarations or roots differing from the manifest. Release roots still belong to native system folders, and whole selected systems remain the payload ownership unit. The installed generation loads the pinned control as an adopted root instance so direct distribution references continue to resolve. `packSnapshot` retains its existing native-folder declaration requirement.

Root release controls separate publication selection from vocabulary ownership. They do not create dependencies on every system named by other release controls. Per-system packages explicitly depend on workspace-system for their release declaration and generated installation workspace vocabulary. Workspace-system therefore keeps its agent/compliance foundation closure; generated teaching guides retain their actual schema dependencies. Native and npm versions remain independently selected.

Packing (2026-10-09, milestone position-packet plan amendment B7) refuses a release descriptor that names no `distribution`, which the database's descriptor decoder admits for a workspace that releases nothing, as `IA-DIST-CLOSURE-INVALID` as soon as it decodes the descriptor, after it verifies the snapshot's sources and before it admits them, computes the release closure or writes anything; a descriptor that names one packs as before.

The host projection mechanism (`./projection`; 2026-10-09, milestone position-packet task replace-renderers, plan amendment B9) plans and applies the files a caller renders, each carrying the marker the caller passes, at the exact `PROJECTION_PATHS` of each host: `.claude/rules/ia-workspace.md` and `.claude/skills/ia-authoring/SKILL.md` for Claude, `AGENTS.md` and `.agents/skills/ia-authoring/SKILL.md` for Codex, and since milestone generation-binding task host-consumes-generated-set (plan amendments C4, C5 and C12) the generated files `GENERATED_PATHS` names: `.claude/agents/<name>.md` and `.claude/skills/<name>/SKILL.md` for Claude, `.agents/skills/<name>/SKILL.md` for Codex, each a lower-case portable name (`projectionOwnable` is the union). A generated file carries the packet marker and is a planned write owned through the same state; an owned one no render writes any more is removed when it still carries an owned marker (an agent through the legacy path below, which deletes only a marked, unedited file; a listed skill without the marker is the user's, kept as `foreign` and dropped from the state, H-N10), and the skill folder that removal empties is removed too, never recursively (H-N6); a generated skill is refused (IA-DIST-LOCAL-MODIFICATION) where its folder already holds files and the state owns nothing in it (H-N11), located at that folder and naming it as `skillFolder`, so the caller names the files to move (A-F2), a user's own unmarked SKILL.md there included, so the refusal converges in one hop (F6); the packet's own `ia-authoring` skill keeps the file rule; an unmarked or hand-edited file at a generated path is refused, never overwritten or removed; a generated agent is refused (IA-DIST-PATH-UNSAFE) where `.claude/agents` is a link. A generated agent at the path of an owned 1.x steward file replaces it as one update: the legacy pass skips every path an artifact writes, so no plan holds an update and a remove for one path. Besides the caller's marker, the two 1.x markers (`<!-- Generated by tools/projections/generate.ts; edit the cited native records. -->` and `<!-- Generated by ia host; edit the cited native records. -->`) are owned, so a file a 1.x renderer wrote is replaced in place rather than refused. The ownership state format `ia.host-projection-state.v1` is unchanged, and a Claude state may still list `.claude/agents/<name>.md`, for removal only: the planner plans `remove` for each listed one that carries an owned marker and is unedited (a listed one already gone only leaves the state), refuses a listed marked one edited by hand as it refuses any owned file, and lists every other agent file, a listed unmarked one and any the state does not list, marked or not, as `foreign`, which no apply writes or deletes. The final state lists only the files rendered. `observeProjection` reports no drift for a listed steward file that is gone or unmarked. The CLI's `applyHostProjection` is the one caller that applies these plans; the steward-guard registration it retires first is `./guard-registration`'s removal, with the safety checks below.

The installed-implementation catalog (`./implementations`; milestone generation-binding, plan amendments C16 and C24) is the `implementations.json` file, format `ia.installed-implementations.v1`, that the host payload builder generates and inventories; the builder finds each first-party implementation package only in the repository's own `node_modules` and imports its declaration module at build time to read the declaration, which no host app ever imports. Its value's shape is `@inventarch/db/distribution`'s (`checkInstalledImplementations`), which binders read too: an `evaluators` section that is an `ia-evaluator-catalog/1.0` value with no installed entries (the built-ins are implicit), and an `operations` section listing each first-party installed operation implementation `available` (descriptor version, operation identity, handler, input and output validator ids, the payload path of its shipped handler module, that module's SHA-256 and the installed packages of its closure), `unavailable` or `revoked`, each with a reason. `readInstalledImplementations(directory, release, verify?)` first verifies the whole payload as `verifyHostCache` does (which now also returns the verified inventory) and requires it to verify as `release`, a release.json that does not hash to it refusing before it is parsed: a file anywhere in the payload directory that the inventory does not list (nothing outside that directory is verified), a link, a missing file or changed bytes refuse with that verification's code, so nothing is ever read, let alone available, from a payload that fails verification. The catalog is the file that verified inventory lists, read again against its pin; an available operation whose handler module or closure package manifest the inventory does not list is `unavailable`, and one whose handler digest disagrees with the inventory is `IA-DIST-INTEGRITY-MISMATCH`. What binds an implementation is its handler module's digest together with the verified inventory, which pins every other byte of its closure (review finding B-N5); the composition descriptor's own `implementationDigest`, which hashes the installed package trees of the process that imports it, is a producer-side pin the catalog does not record, and a bundled host's counterpart is the payload release digest a join records. A v1 payload, or a v2 payload whose inventory lists no catalog, reads as `unavailable`, not as damage. It never imports, loads or runs a handler. `joinHost(root, host, consumerRevision)` records, under the host lock and after a pending-journal check made under it, the host's row in `.ia/distributions/hosts/joins.json` (format `ia.host-joins.v1`: consumer, implementation `installed-implementations`, payload version, catalog digest, payload release, consumer revision), derived from the committed `<host>-workspace.json` registration and the catalog of the payload it names; with no registration or no catalog it drops that row instead. `leaveHost` drops a row; unreadable receipts refuse, located at the file, rather than being replaced.

Execution bindings (milestone generation-binding task execution-binding-host-entry, plan amendment C24): a catalog row may also be `revoked`, with a reason, which binders report as an error. `joinedCatalog(root, trust)` finds the catalog a workspace's host joined, as `trust` (`HostTrust`: the validating installation's IA home and the payload release it pins) allows. Only `<home>/hosts/<release>` is ever opened: a join counts only when it and its host's registration name that release and the registration names that payload directory, so a registration of another release, or of a payload anywhere else (another IA home, inside the workspace, a network path), is `unavailable` with the repair `ia host <host> --apply` and nothing it names is opened (review finding B2-R2). That payload is read once; a payload that fails verification with changed or unlisted files, a link, exceeded limits or a release.json that does not hash to the pin (parseable or not) is `damaged`, whichever trusted join names it, since every trusted join names the same payload (B2-N1, B2-N2); otherwise the first trusted join in consumer order that carries the payload's catalog digest is the source. With no receipt, no trust (null) or no trusted join that holds, the catalog is `unavailable` with the reasons. `installationTrust()` is the trust of the distribution module's own installation: the payload it runs from, `<home>/hosts/<release>/runtime/node_modules/@inventarch/distribution`, or null outside one. `WorkspaceSession.bindings(trust)` joins every admitted `@execution-binding` with it (`@inventarch/workspace-runtime/bind`) and returns the catalog source and one result per binding; `ia-distribution validate` passes `installationTrust()`, adds that result as `bindings` and exits 1 when a binding is revoked. It reads only.

Check binding and evidence (task check-runner-join-validate, plan amendments C14, C15, C21, C22 and C23): `openWorkspaceSession({root, checks})` passes db `OpenOptions.checks`; every other caller keeps strict admission. A session never reads evidence (review finding B3-R4), so what a validation admits, binds and reports is the authored view's alone, and `validation()` reports `revision`, the one every other reader reports, and `authoredRevision` (B3-N4). `WorkspaceSession.checks(trust)` binds every admitted `@check` with db `bindChecks`, a catalog evaluator against the same catalog `bindings(trust)` reads (`joinedCatalog`, read once per session and trust), and returns the catalog source (null when every check names a built-in evaluator, and then no catalog is read) with one result per check; `validation()`, `bindings()` and `checks()` read only. `recordValidation(session, checks)` is the validate request and the one writer of evidence: it records the session's bound checks that passed or failed through db `evidenceText` and `writeEvidence` at the session's authored revision, reading the current file only for the times an unchanged observation keeps; nothing when the vocabulary has no `@observation` word, and nothing recorded or pruned when admission is refused (B3-N11). Only writing this revision's file can refuse: a directory or file the process cannot write as IA-DIST-EVIDENCE-UNWRITABLE, located at `.ia/work/evidence`, and a link or misplaced entry as db IA-DB-PATH-UNSAFE; pruning other revisions' files is best effort and keeps what was modified after the session opened (B3-R1, B3-N2). `ia-distribution validate` opens a structural session, adds `checks` and `evidence` to its result, and exits 1 when a binding or a check is revoked. Two trust roots (review finding B3-N8): `ia validate` trusts the payload its bundled pin names in the IA home, while `ia-distribution validate` trusts only the payload it runs from (`installationTrust`); run from a package install or a checkout, outside any payload, it trusts no join, so its catalog is unavailable and no catalog check or execution binding binds where `ia validate` may bind them.


PR #30 upgrade safety: `assertRetirableGuard` inspects both Claude settings locations and refuses unmatched IA guard groups before a caller deletes steward files, preserving unrelated settings. Guard removal accepts a recorded old-root group only in the fixed released shape and only when the current group matches the recorded bytes; registration and execution retain strict current-root validation. A linked legacy agents directory is foreign and never traversed; listed paths beneath it are left untouched. `legacyProjectionActions` exposes removal/foreign actions independently of active files that an install refresh will render after activation.

Hook groups (`./guard-registration`; 2026-10-11, milestone generation-binding plan amendment C9): `planHookRegistration(root, {cache, hooks} | {remove})`, `planHooksFor(root, expected, hooks)` and `applyHookRegistration(plan, checkpoint?)` plan and apply exactly one PreToolUse group in `.claude/settings.local.json` per hook row `{identity, tools, paths}`: the matcher is `Write|Edit|MultiEdit` whatever the row's tools (which are validated and reported, and which the guard applies to the hook's paths from the record), so the guard's managed-state protection decides every edit tool, and the one handler runs the launcher's guard mode as `guard --root <root> --hook <identity>`, in the derivation the retired steward guard's group used (direct on win32, `/bin/sh` with `FAIL_CLOSED` elsewhere, timeout 10). Nothing authored but the identity, a canonical `system/kind/facet/name` of at most 512 characters, and the tools reaches a group. Rows are held to the bounds hook generation applies (workspace-runtime `HOOK_LIMIT`, `HOOK_SELECTION_LIMIT` and `registrableSelection`: at most 64 hooks, each with one to 64 selections of at most 512 characters), so a hook beyond them is reported by generation, never refused here. The groups are owned by exact match against `.ia/distributions/hosts/claude-hooks-<id>.json` (`ia.hook-registration-state.v1`), which also records each hook's registered `paths`, the selection the guard refuses when the hook's record can no longer be read: a plan replaces an owned group whose derivation changed in place, appends a new one, removes one no longer requested, and keeps every other group, key and byte, so a re-plan of the same rows writes nothing and removing the last hook restores the settings byte for byte, except that a container the groups emptied which existed before is written as `[]` or `{}` whatever whitespace it held (a file the first registration created goes again, and containers it created are pruned). It refuses an owned group changed or duplicated by hand, an unmanaged group identical to one it would write, `disableAllHooks` when it would create or update a group (a plan that only keeps or removes owned groups proceeds), a consumer root inside the cache, and a malformed or repeated row; an owned group the user deleted only loses its ownership when its hook is no longer requested. Publication holds the host lock and uses the guard's journal, `guard-pending.json` with format `ia.hook-registration-pending.v1`, which every host write already waits on and `recoverGuardRegistration` (`recover-guard`) finishes or rolls back. `assertRetirableGuard` and the retired guard's removal recognize only a guard group that names no `--hook`, so hook groups never block B11's retirement. `readHookRegistration(root)` reads the hook ownership state, `observeHookRegistration(root)` reports each owned group `missing`, `modified` (changed or duplicated) or `foreign` (a guard group naming `--hook` for this root that no state owns), read-only, and `hookGroupDigest(group)` is the SHA-256 a receipt lists for a group, and `hooksDisabledBy(root)` names the settings file whose `disableAllHooks: true` turns hooks off, read as registration reads it (H-N12). The CLI's projection writer registers and removes the groups (apps/cli SPEC, the generated set).

Registry collection kinds, source-only workspace adoption, kit installation, budgets and rollback are specified in [registry collections](references/registry-collections.md).

An installation plan whose lock requires an unsupported distribution engine refuses with `IA-DIST-CONFLICT`, naming its required range and the current installer engine. Installed reads distinguish `engine-incompatible` from corrupt state through the database error reason. Neither restore nor recovery upgrades the running implementation; no fallback rewrites a lock or lowers an archive engine range. The compatibility and rollback procedure is documented in [README.md](README.md).
