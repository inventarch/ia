# Consumer CLI contract

This contract describes the `ia` consumer shell: how it parses a command, which commands write, how it refuses and what it prints. The package [contract](../../../apps/cli/SPEC.md) records each command's detailed behavior. The [command table](../../../apps/cli/src/commands.ts), [parser](../../../apps/cli/src/args.ts) and [shell](../../../apps/cli/src/consumer.ts) are its executable owners. Section numbers are stable because source comments cite them; retired sections keep their numbers unused.

## 1.2 Dispatch and discovery

The command table owns command names, arguments, options, help and handlers. Parsing runs before any workspace, cache or registry read, except the hand-off below, which reads only directories and `package.json` files. An unknown command is a usage error that names the nearest command, or `ia --help` when none is near; an unknown option names the command's `--help`. Operation help comes from the runtime's [machine protocol](../../../packages/runtime/src/machine-protocol.ts), so the supported operations and their input shapes have one owner. Workspace commands use the nearest ancestor that holds `.ia/src`; `--root` names another root where a command accepts it. When no ancestor holds `.ia/src`, or `--root` names no directory, the command refuses with `IA-DB-ROOT-INVALID` at exit 3. A directory whose `.ia` is the IA home is never a workspace. `ia <operation> --help` and `--schema` print help text at exit 0, `--version` prints the version, and the token `agent` is reserved: `ia agent` refuses as `IA-CLI-USAGE`.

Hand-off is the first step, before parsing, and reads only directories and `package.json` files, then asks git once whether the local copy is committed. A command typed into an `ia` runs on the `@inventarch/cli` the workspace pins and has installed whenever that copy is not the running one, older or newer, and that copy produces every byte of output and the exit code. The workspace is the first `--root` before `--`, at its real path as the command opens it, and without `--root`, the one discovery finds from the working directory; a `--root` without `.ia/src` means no hand-off. The pinning manifest is the nearest `package.json` at or above the workspace; when it lists `@inventarch/cli` in `dependencies` or `devDependencies`, the first `node_modules/@inventarch/cli` from the workspace up to the manifest's directory is the local copy. The running copy starts that copy's `bin` entry with the same Node, the same arguments and the same stdin, stdout and stderr, with `IA_HANDOFF_FROM` set to the real path of its own package root, and exits with its exit code, or 130 when it ended on a signal. While that copy runs, the running copy ignores `SIGINT`, `SIGTERM`, `SIGHUP` and, on Windows, `SIGBREAK`. A signal sent to the whole foreground group, such as a terminal's Ctrl-C, reaches the copy handed to as well, which acts on it, and the running copy exits only after it. A signal sent to the running copy alone is ignored and not forwarded; it exits when the copy handed to does. Any non-empty `IA_HANDOFF_FROM` means the running copy never hands off again. There is no hand-off for bare `ia`, for `--user` before `--`, for an extension's command token, for `doctor --host`, when `IA_NO_HANDOFF` is `1`, when an IA home variable is malformed (the running copy refuses it as before), without a workspace, a CLI dependency or a valid local copy, when the local copy is the running one by device and inode, or when git tracks any file of the local copy: a copy the repository commits is the repository's code, not one an install wrote, so a typed command never runs it (without git, or outside a repository, nothing is tracked). Hand-off reads the tokens without parsing them, so an option value spelled like `--user` or `--root` routes as that flag; the running copy then answers, or the `--root` it names decides. A local copy that is installed but cannot be started is reported on one stderr line, `ia: could not start this workspace's @inventarch/cli <version> (<reason>); running <own version> instead`, and the running copy answers; hand-off itself never writes to stdout. A local copy that starts and then fails while loading, as one an interrupted `npm ci` left behind can, ends the command with its own failure: that failure is the workspace copy's, and `IA_NO_HANDOFF=1` runs the typed `ia`'s own. In a workspace that hands off, `ia --version` and `ia --help` answer from the workspace's copy; `IA_NO_HANDOFF=1` gives the typed `ia`'s own. The handed-off copy runs with the workspace's trust: it is the code `npx ia` runs there, and the copy the `init` skill grounds on, the "repository's pinned `@inventarch/cli` when it is installed" ([host-plugin-distribution](../host-plugin-distribution/README.md) §6.1). In a checkout that is not trusted, `IA_NO_HANDOFF=1` is the opt-out: the `ia` that was typed answers. The session hook sets it (host-plugin-distribution §8.2), so the hook never hands off. `runCli` and `dispatch` never hand off; only the `ia` executable does. That is the package's `bin`, `dist/bin.js`, which decides before it loads any command module. `node dist/main.js`, the plugin hook's entry, runs that copy and never hands off.

Bare `ia`, with no arguments, opens the console only when stdin and stdout are both terminals and `CI` is unset or empty; a bare invocation carries no `--json`. Everywhere else, in a pipe, under redirection or in CI, it prints byte for byte the help `ia --help` prints, at exit 0, and `ia --help` always prints help. The console is a full-screen view of one workspace built from `doctor`'s rows (§2.12): areas that show the worst status of the rows they group, offers derived from each row's `fix` and a few recipes, and for the selected offer what it does, the commands it runs and what they change. Rows the running copy owns (`install-channel`, `ia-home`, `plugin-claude`, `updates`, `updates-account`, `workspace-decision` and every row an extension declares) come from the running copy; every other row comes from the workspace's own copy's `doctor --json --root <root>`, run with `IA_NO_HANDOFF=1`, when that copy is installed and is not the running one. A run that does not exit 0 or 1 with a version 1 report marks those rows `unknown` with its cause, and a copy that predates `cli-version` has only that row computed for it. An offer runs in the normal screen with inherited stdio: a form that previews runs its preview, then the console asks and runs the confirmed form (§2.12's `confirmedArgv`); each `ia` step runs as `process.execPath <entry> …argv` with `IA_NO_HANDOFF=1` on the copy resolved at that step (the running copy for a step that writes the user's home or the machine, else the workspace's own copy, else the running one), and an external step runs the program its fix names, found on qualified PATH entries. The console itself never hands off. `q`, Escape or Ctrl-C quits with exit 0.

Outside any workspace bare `ia` opens the all-workspaces view over the tracked list (§2.16), with "Find workspaces in a folder…" highlighted when the list is empty; inside one it opens that workspace's view, and tab switches between the two. The view shows a summary (the cached latest release, the running version, and how many tracked workspaces are healthy, need attention or are missing, and, when not zero, unreadable, unchecked or still loading) and one row per tracked workspace. Each row is read the way the single-workspace view reads its own: that workspace's copy's `doctor --json --root <root>` with `IA_NO_HANDOFF=1`, at most four at once and each bounded at 30 s, a row showing `?` until its result arrives (refreshing a workspace opened from the table shares those four runs; a newer refresh, leaving it or opening another cancels one still running, a result is kept only while that same workspace is still open, and quitting aborts every run); a row whose root is gone or holds no `.ia/src` is missing and is not read. A row's class comes from the statuses its own checks report, never from its offers, so a failure whose remedy is advice still needs attention. Enter opens a row's own view, from which Escape returns. Space selects rows, `a` selects every row where a batchable offer fires, and `b` moves to the batchable offers on the selection; `f` opens a folder line, in which every character is text, and tracks the workspaces found under that folder that the user selects.

A batch applies one batchable offer to the selected workspaces, each in a new git worktree on a new branch `chore/<offer>` (`chore/ia-3-5-1` for an upgrade to 3.5.1). Its preview names each worktree, branch and command, and one confirmation runs it. For each repository, one at a time, a failure stopping only that one: `git fetch origin`; the base is the first of `origin/HEAD`, `origin/main` and `origin/master` that resolves, else the repository is refused; an existing worktree path or branch is refused; `git worktree add --no-track -b <branch> <path> <base>`, so the branch never has an upstream. The worktree is `<parent of the repository>/.ia-worktrees/<repository>-<branch without chore/>`, or under `worktreeRoot` in the IA home's `config.json`; a worktree root inside the IA home, or a worktree inside the repository, is refused. When the worktree holds a `package.json`, the package manager's install, built for the worktree, runs first; a manager conflict or no manager refuses the repository. Then each step runs with its working directory in the worktree (the workspace's own subfolder when the workspace is not the repository's top level): an `ia` step on the copy the worktree has at that step, or on the running copy when it has none, in its confirmed form. Steps that write the user's home or the machine are left out of every repository's run and offered once afterwards. Every path-bearing argument of every step is rebuilt for the worktree: resolved against the step's working directory there, an absolute path inside the repository moved to the same place in the worktree, and anything that leads outside the worktree refuses the repository. Before anything is fetched or created, the worktree path is judged by where it really leads (the real path of its nearest existing folder, joined with the rest), so a `worktreeRoot` or `.ia-worktrees` folder that is a link into the repository or the IA home refuses the repository. Immediately before the install and before each step the real filesystem is checked again, so a link that leads out of the worktree, committed or made by an earlier step, refuses the repository at that step; so does an `ia` entry whose real path is outside the worktree (only the running copy's own entry may be), and a program found on PATH whose real path is inside the repository. No batch child inherits git's repository-local variables (those `git rev-parse --local-env-vars` lists, such as `GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE`, and `GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>`), which would route even `git -C <worktree>` elsewhere. The user's own checkout, dirty or not, is never read or written: the only commands that name it are git metadata operations run as `git -C <its top level>` (`rev-parse --show-toplevel`, `fetch origin`, `symbolic-ref --quiet refs/remotes/origin/HEAD`, `rev-parse --verify --quiet`, and `worktree add --no-track -b`). After the run a results table and a "next" list follow, each entry a separate choice: commit those that passed as `chore: <offer title>`, with nothing added; commit, push and open PRs (a create-only `git push --atomic --force-with-lease=refs/heads/<branch>: -u origin <branch>:refs/heads/<branch>`, so a branch already on origin, even at the base commit, is reported as a collision and left as it was; then `gh pr create --fill --head <branch>`), offered only when `gh` is found and `gh auth status` exits 0, a rejected push reported for its repository while the others continue; open a failed repository; remove the worktrees, keeping their branches. Nothing is pushed unless that choice is made.

## 2 Commands and arguments

### 2.0 Grammar

Long options accept `--flag value` and `--flag=value`. Boolean options, an explicit `--`, repeatable options and repeated positionals follow each command's grammar. One-letter aliases such as `-y` and `-q` are exact tokens; a bundled form such as `-yq` is an unknown option. Closed value sets, integer bounds, conflicts and required arguments are checked before dispatch. Every parse refusal is `IA-CLI-USAGE` at exit 2.

Every `--apply` (`init`, `adopt`, `install`, `update`, `remove`, `restore`, `project` and `host`) confirms the same way. On a terminal without `--yes`, an apply shows the change summary and accepts only `y` or `yes`, in any case, ignoring surrounding space. Declining exits 0 and applies nothing. An apply without a terminal, or with `--json`, requires `--yes`.

### 2.1 Initialization

`init [directory]` previews. `--apply` installs the bundled language base, writes the three starter records and the release descriptor, and captures the workspace. The target is positional, so `--root` is refused. `--host claude` or `--host codex` also runs the host registration path, and `--host none` skips it. `--id` sets the package id, and `--system` also authors a local `@system` and `@distribution`. `--from <plugin-directory>` lowers a host plugin as a kit, `--migrate` rewrites a 1.1.0 starter, and `--adopt <id>` mounts a registry workspace. `--decline` and `--forget-decline` record or clear, in the IA home, that a repository should not be initialized; they write nothing in the repository. Once `--apply` has initialized the target, `init` offers to add it to the tracked list (§2.16). See [initialization](../workspace-initialization/README.md) and [apply](../workspace-initialization-apply/README.md).

### 2.2 Vocabulary and 2.3 formatting

`vocabulary` reads the word catalogue bundled with the CLI and opens no workspace, so `--root` is refused. `--schema` and `--example` require a word. `format` checks formatting by default and rewrites files only with `--write`.

### 2.4 Capture and 2.5 validation

`capture` admits the workspace and writes its snapshot to `.ia/work/snapshot/current.json` through the database service. `capture --preview` reports what it would write and writes nothing.

`ia compile` is removed. Every invocation returns `IA-CLI-USAGE` (exit 2) and names `ia capture --help` before it opens a workspace. It is absent from help and the catalog, and its token stays reserved so an extension cannot take it over. The published internal compile helpers keep their signatures for programmatic callers.

`validate` reports language and contract findings, then execution bindings and checks separately. A check with no bound evaluator is `not-evaluated`, never a pass. `validate` records the bound checks that passed or failed as evidence under `.ia/work/evidence/`, keyed to the authored revision it checked. A validation whose admission is refused records and prunes nothing; under `--verify-conformance` that is the admission without verification. `validate` never writes authored records.

`validate --verify-conformance --require-verified` (opt-in) exits 1 unless COMP-KERNEL and COMP-FIXTURES are both verified passes; without `--require-verified` the exit is unchanged. `validate --verify-conformance` verifies COMP-KERNEL and COMP-FIXTURES in-process with compliance's `package-v1` profile and reports them with `basis: 'verified'`, plus the profile and the suites it does not run. A floor that differs from the embedded one fails COMP-KERNEL and exits 1. The evidence it records is what `validate` without the flag records, even when verification refuses the report. Without the flag the output is unchanged.

### 2.6 Inspection and 2.7 packing

`inspect`, `read`, `position` and `next` are observations and write nothing. `read` returns the body behind a locator with its digest. A position packet is a navigable context surface, not a body.

`pack` requires `--descriptor`. A descriptor that names no `distribution`, which a default `init` writes, is refused as `IA-CLI-CONFLICT` (exit 3). An ordinary consumer workspace is therefore not publishable until it has a `@distribution`, which `init --system` authors.

### 2.8–2.11 Distribution changes

`install`, `update`, `remove` and `adopt` plan by default and apply only with `--apply`. `restore` has no preview and requires `--apply`. An apply rechecks the plan's inputs, and confirms as §2.0 describes.

After the installed set changes, registered host projections are refreshed. A refresh that fails after the install committed refuses at exit 3 and says that the installation is applied. `ia recover [installation|host|guard|lifecycle] --root <directory>` repairs an interrupted installation, host, guard or lifecycle transaction; `--root` is required. See [registry](../registry/README.md).

### 2.12 Doctor

`doctor` reads state and returns `ok`, `info`, `warn`, `fail` or `unknown` rows, one status per row. A check that did not run is `unknown`. Doctor exits 1 when any row is `fail` and 0 otherwise. It does not repair anything or start servers. See [host observations](../host-registration/README.md#7-doctor-and-support).

Each row carries a `remedy`, display text or `null`, and beside it a structured `fix`: `{program, argv, flow, writesTo}` or `null`. `program` is `ia` (`argv` excludes the leading `ia`) or `external` (`argv[0]` is the executable, such as `npm`). `writesTo` is `none`, `repo`, `user` or `machine`. Advice gets `fix: null`: a remedy that is prose, offers two commands, or chains steps with ", then". The display of a fix is always derived from its `argv` with the same quoting as every printed command; it equals `remedy` wherever the remedy is one runnable command, and a fix whose remedy names no directory (an install for a manifest in an ancestor directory) carries that directory in its own argv. For an `ia` argv the flow is read from the form parsed under the grammar of the action it names (the first positional of a command with actions, such as `workspaces add`, whose options another action owns refuse), and the first rule that holds decides: an option given that conflicts with `--apply` is `confirm`; a required `--apply` is `confirm`; an optional `--apply` is `preview-apply`; a `--preview` option is `preview-flag`; the action's or command's declared flow (`recover`, `workspaces add` and `workspaces remove` declare `confirm`); a read or validate catalog mode is `immediate`; otherwise the fix is `null`. A form that does not parse has no fix, and a form that requires `--root` gets the root appended. An `external` fix is always `confirm`. A console previews with `previewArgv` (a `preview-apply` form without `--apply` and `--yes`, a `preview-flag` form with `--preview`; none for `confirm` and `immediate`) and, after its own confirmation, runs `confirmedArgv`: a form that applies gains `--apply` when it is `preview-apply` and lacks it, and `--yes` when its grammar has one, so a child on piped stdio is never refused or asked twice; every other form runs as given. An extension command, which no core grammar describes, follows its declared flow: a `preview-apply` form confirms with `--apply` added once, and no `--yes`. Check ids are an open set: a reader accepts ids it does not know. [Host plugin distribution §7.3](../host-plugin-distribution/README.md#73-doctor) lists the rows.

### 2.13 Preview and author

`preview` shows what one new record, one field change (`--set`) or one relationship (`--relate`) would compile to, with the findings it would add and the target file's current `sha256`. It writes nothing.

`author` takes the same arguments plus `--digest <sha256>`. It writes only when the target file still has that digest and the candidate is clean, and it adds one attribution comment naming the acting participant, its mandate and the authored revision. A changed file refuses as `IA-CLI-EDIT-STALE` and a candidate with errors as `IA-CLI-EDIT-UNCLEAN`, both at exit 1 and with nothing written.

`author` refuses the administrative words `workspace`, `agent`, `mandate`, `system`, `schema`, `agent-profile` and `hook` with `IA-CLI-EDIT-AUTHORITY`. An owner changes those records in source and runs `ia validate`.

### 2.14 Projection and host registration

`project <claude|codex>` plans, or with `--apply` writes, the position packet's files for one host and registers nothing. `project <claude|codex> --product plugin --out <directory>` writes the plugin a lowered workspace describes, and `--product plugin --check` compares it in memory, writing nothing. `host <claude|codex>` plans, or with `--apply` applies, the workspace's host registration, and `host --remove` plans removal of the owned host set. `host claude --user` installs a user-level plugin. All of them plan by default. See [host registration](../host-registration/README.md) and [host plugin distribution](../host-plugin-distribution/README.md).

### 2.15 Mandate checks

These commands are judged against the acting participant's governing mandates before they run:

| Move | Commands |
| --- | --- |
| Observation | `read`, `next`, `kb search/read/resolve/traverse` |
| Verification | `validate`, `preview`, `kb check` and `kb pack` preview |
| Synthesis | `author` |
| Execution | `capture`, `project`, `kb pack --apply` and a workspace `host --apply` |

A capture or project plan is judged as the effect it plans. No other command is judged, including `position`, `inspect`, `init`, `doctor`, the distribution commands, the machine protocol, and a `host` plan, `--remove` or `--user`. Each judged command takes `--actor <agent>` to name which authored participant is acting.

A refusal is `IA-RUNTIME-MANDATE-MOVE`, `IA-RUNTIME-MANDATE-WORD` or `IA-RUNTIME-MANDATE-ACTOR` at exit 1, and its next command is usually an `ia position` command for the mandates that govern there. `ia position` is never judged, so that command always runs. While an authored `@mandate` fails admission, including one stating `authority.moves []`, every judged command refuses with `IA-RUNTIME-REQUEST-INVALID` and names `ia report`, which shows the admission findings. A mandate is a cooperative restriction on these commands. It is not authentication or a sandbox, and it grants no host permission.

### 2.16 Workspace tracking

`workspaces` keeps one person's list of the workspaces they keep current in the IA home, at `<IA home>/tracked-workspaces.json`. The file is `{"format": "ia-tracked-workspaces-1", "workspaces": [{id, root, label?, added}]}`: `root` is an absolute real path and `added` an ISO-8601 UTC time. A rewrite keeps every top-level key and row key it does not know. A file that does not parse, or names another format, is refused as `IA-CLI-TRACKED-INVALID` at exit 3 and is never overwritten. Tracking is not admission: it never reads or writes the MCP door's `workspace-locations.json` and admits no workspace to the door.

The command opens no workspace, so `--root` is refused. It has four actions:

| Action | Writes | `--json` |
| --- | --- | --- |
| `list` | nothing | `{version: 1, workspaces: [{id, root, label, added, state}]}` |
| `add [directory] [--id <id>] [--label <text>]` | at once | `{version: 1, status: 'added' \| 'already', workspace: {id, root, label, added, state}}` |
| `find <folder> [--depth <n>] [--apply]` | only with `--apply` | `{version: 1, folder, found: [{root, tracked, id}], applied, added: [id]}` |
| `remove <id\|directory>` | at once | `{version: 1, removed: {id, root, label, added}}` |

The human `list` and `find` tables keep to the terminal width: the root keeps at least 20 columns and a long id is shortened in the middle to what is left, while `--json` carries every id and root whole. On a terminal too narrow for those minimums, the rows are stacked instead, one block per row: the id, then the root, then the state. Every stacked line keeps to the width, down to one column: the indents give way first, the id and root are shortened in the middle, and the state word is shortened at its end, after its symbol while the symbol fits. `label` is `null` when a row has none. `state` is `present`, or `missing` when the root is gone or holds no `.ia/src`; a missing row stays in the list until it is removed by name. `add` and `remove` change only the user's own list and print exactly what changed. `find --apply` confirms as §2.0 describes, and tracks every untracked workspace it found in one write. An action that does not read an option refuses it as `IA-CLI-USAGE`.

`add` without a directory tracks the workspace that holds the working directory. The root must hold `.ia/src` (`IA-DB-ROOT-INVALID`) and lie outside the IA home (`IA-DIST-PATH-UNSAFE`). Roots that exist are compared by device and inode alone, so a junction, a trailing separator or a different case on Windows is the same row, two directories whose names differ only by case on a volume that keeps them apart are two rows, and adding a tracked root again reports `already`. Where either root reports no identity (an inode of 0 or all ones, as some network and ReFS volumes on Windows do), the two real paths are compared exactly instead, never case-folded. The folded spelling is compared only when one of the two paths no longer exists. A row's id follows `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`, the door's own rule; another `--id` is usage, refused before the tracked list is read or a root is discovered, so a malformed list never hides it. The default is the `@workspace` name when the workspace's `.ia/src` declares exactly one at column 0, found by a lexical scan of at most 200 `.ia` files, or else the folder name, lower-cased, with every other character a `-`. The following refuse at exit 3 and write nothing:

- `IA-CLI-TRACKED-ID`: the id is already tracked for another root. The message names both roots, and the next command adds the root under a free `--id`.
- `IA-CLI-TRACKED-EXISTS`: a new `--id` or `--label` is given for a root already tracked. The next command removes the row first.
- `IA-CLI-TRACKED-UNKNOWN`: `remove` names no tracked id or root.
- `IA-CLI-TRACKED-LOCKED`: another owner holds the list's store lock and did not release it within 10 seconds, measured on a monotonic clock. The message names the lock path, `<IA home>/tracked-workspaces.json.lock`, and its owner's pid and host, or says the owner could not be read. When the owner is on this host and its pid is no longer running, the message says so. The next command says to delete the lock by hand only when no `ia` process is running on that host.

Every mutation (`add`, `remove`, `find --apply` and the `init` offer) takes that lock before it reads the list and holds it through validation and replacement, so processes running at once each keep their rows. The lock records its owner (pid, process start time where the platform reports one, host and creation time). `ia` removes only a lock it published itself. It never renames or deletes a lock another owner holds, whether that owner is running or gone and however old the lock is, so a lock left by a killed process blocks every mutation until it is deleted by hand.

`find` walks the folder to `--depth` levels below it (default 4, at most 8). It skips `node_modules`, `.git`, `.ia-worktrees`, every folder whose name starts with `.`, the IA home, links and junctions, and a folder whose `.git` is a file, such as a linked worktree or submodule. It does not descend into a workspace it found, so fixtures inside a repository are not listed. The folder `find` is given is held to the same exclusions and skipped as the walk skips them, not refused: a link or junction (judged before it is followed), a folder whose name starts with `.`, one inside the IA home, one named `node_modules`, `.git` or `.ia-worktrees`, or one holding a `.git` file finds nothing, and `find` reports none found under it.

After `init --apply` initializes a target that is not yet tracked, `init` offers to track it. On a terminal without `--yes`, it asks `Track <root> in your workspace list? [y/N]` and tracks on yes. Otherwise it prints one stderr line, `Track it with: ia workspaces add <root>`, and writes nothing. Under `--json` it says nothing. A root already tracked, or an IA home that cannot hold the list, gets no offer. A tracking failure is one stderr line and never changes `init`'s exit code.

## 3 Exit classes and protocol boundaries

The consumer shell returns 0 for success, 1 for failed validation or a semantic refusal (a mandate refusal included), 2 for usage, 3 for state, I/O and conflict failures, 4 when `install`, `update` or `restore` cannot reach or read a remote registry or archive (`IA-DIST-ARTIFACT-UNAVAILABLE`, or a remote `IA-DIST-LIMIT-EXCEEDED`), and 130 for interruption.

The machine protocol keeps its own boundary. Its operations are `scope`, `context`, `select`, `get`, `records`, `resolve`, `search`, `traverse` and `report`. Each prints one JSON line on stdout with no color and nothing on stderr, exits 0, 1 or 2, and carries no consumer `next`. Consumer formatting and flags never leak into it. The `ia-distribution` binary keeps its own protocol too, and never exits 2. [Protocol tests](../../../apps/cli/tests/protocols.test.ts) exercise the built entrypoints.

## 4 Refusals

A refusal keeps the service's code, location and reason, and names one command to run next. It does not turn unknown or interrupted work into success. Effects that already completed are reported as completed.

## 5 JSON

`--json` prints one parseable value to stdout. Prompts and incidental process output never share stdout. A parse-time refusal reads no workspace or installation state.

`ia doctor --json` is `{version: 1, checks, counts}`, plus `session` and `nextActions` with `--host`. Each check is `{id, title, status, detail, remedy, fix}`; `fix` (§2.12) was added beside `remedy`, and every other key and value is as it was.

A refusal is `{version: 1, ok: false, code, message, exit, where, next}`. `where` is `{path, line, identity}` or `null`, `next` is the one command to run next, and `details` appears when the refusal carries one. An interruption is `{version: 1, ok: false, code: 'IA-CLI-INTERRUPTED', message, exit: 130, next}`, with no `where`; its `next` is also printed on one stderr line.

## 6 Terminal rendering

Human output is rendered from structured tokens, with terminal capability and width handling. `--no-color` (or `NO_COLOR`), `--color`, `--ascii` and `--quiet` adjust it. `NO_COLOR` disables color even with `--color`, and `--json` never prints color. `FORCE_COLOR` and `--color` force it, `IA_ASCII` or a non-UTF-8 locale selects ASCII symbols, and `--color` with `--no-color` is a usage error. Every command prints a terminal state line; progress output is optional. Severity and rendering limits do not change admission.

The console (bare `ia`, §1.2) draws on the alternate screen with the cursor hidden, bracketed paste on and the terminal in raw mode, so scrollback is never touched. It takes these one at a time and, if taking one fails, gives back exactly those it took. One teardown gives back all of them, and turns off the mouse-reporting modes, when the console quits, before a step runs, on an error (printed in the normal screen, exit 1), when writing to the terminal fails (exit 1), on `SIGINT`, `SIGTERM`, `SIGHUP` and, on Windows, `SIGBREAK` (exit 128 plus the signal number: 130, 143, 129, 149), and on process exit; on the paths that end the process (a signal, an uncaught error, process exit) and after an output failure it writes the restoration synchronously, through stderr when stdout has failed and stderr is a terminal. Its handlers exist only while the console runs. While a step's child process runs, the terminal's signals are the child's to act on and the console waits; Ctrl-C at the console's own confirmation declines it. Before a child starts, the console pauses stdin and stops reading it. One offer runs at a time: keys already read when a run starts or the console quits are dropped, and a bracketed paste is never a key, so it neither quits nor runs anything and outside a text entry it is ignored; a paste longer than 65,536 UTF-16 code units is discarded up to its end marker, and so is one whose end has not arrived by the escape timeout; after such a timeout only Ctrl-C is read until that marker arrives (it quits, or cancels the open entry or confirmation, and never runs anything), since a late payload cannot be told from typing. A terminal without bracketed paste cannot tell a paste from typing, so text pasted there in one read is read as the keys it holds. What the console prints in the normal screen (titles, commands, questions, results) shows each argument as written, so a path reads as typed, unless it holds a control character (C0, DEL or C1) or a lone surrogate, starts with a double quote or is empty; that argument is shown as a JSON string literal, with DEL, C1 and lone surrogates escaped. No control character reaches the terminal, and what a confirmation shows reads back exactly (as JSON when it starts with a quote, as written otherwise), while the command that runs keeps its arguments exactly. A Windows `.cmd` program gets each argument that is not plain text in quotes, with backslashes before the closing quote doubled by the Windows argv rules, so the program it forwards to reads back the same argument; one holding `%`, a double quote (cmd.exe has no escape for one, so it would toggle cmd.exe's quoting for the rest of the line) or a C0 control character (U+0000 to U+001F) is refused. It writes only the rows that changed, each frame in one write inside synchronized-output markers, and repaints fully after a resize. Bare `ia` takes no flags, so it reads `NO_COLOR`, `IA_ASCII` and the locale, the environment's forms of `--no-color` and `--ascii`. Text is measured by grapheme cluster with Unicode 16.0.0 display widths, so wide characters and joined emoji keep columns aligned; every cell is cut to its column with `…` and never wraps, and control characters from data are replaced so no escape sequence reaches the terminal. Below 80×20 a one-line notice replaces the view; from 80 to 99 columns the right pane sits below the list.

## 7 Knowledge commands

`ia kb check|search|read|resolve|traverse` opens an immutable, in-memory knowledge view. It reads authored records under `.ia/src` and their explicitly bound UTF-8 Markdown/text bodies. A selector at `.ia/knowledge.json` is optional for local reads. No `.kb`, persistent index or database is created.

`check` reports selected-record admission, reference closure and body availability. Workspace compliance checks are explicitly not evaluated by this scoped view; use native validation for the whole workspace. Missing references and excluded targets are unavailable without disclosing excluded identities or diagnostics. Local citations pin the snapshot and body and refuse after a change.

`ia kb pack --commit <full-sha> --selection <committed-path> --out <workspace-file>` previews a validated immutable package. `--apply` writes it; noninteractive and JSON apply require `--yes`. The output must have existing, unlinked parents within the repository and be outside `.ia`, `.git`, selected inputs and the selector. Identical existing bytes return unchanged; different bytes refuse. Current authority and native revision are checked again after interactive confirmation.

Read operations require Observation; check and pack preview require Verification; pack apply requires Execution. Nested parsing drives both enforcement and retry advice, including explicit `--actor`. The nine existing machine routes retain their protocol. Knowledge results use `{version: 1, ok, value}`; a `check` report that is not ok exits 1. A knowledge refusal uses the §5 refusal envelope with its `IA-KB-*` code and one next command for its cause: malformed input, knowledge outside the scope and an oversized response exit 1; a stale citation, a changed scope or source and an unreadable repository are operational and exit 3. Grammar, workspace, output-path and mandate refusals keep their established codes and exit classes.

The public [KB library](../../../packages/kb/README.md) owns selection, packaging and citations. The application host owns audiences, storage, lifecycle and approval.
